# H-38 — The import review flags abnormal results as if we misread them

## Story
- `/import-review` marks a row *"Needs a look"* with the reason *"Flagged HIGH in the file"*, and
  offers a button reading *"Fix the 3 flagged"*. Those rows were read perfectly. What is abnormal
  is the patient's result.

## Context
Found folding H-15 (2026-09-12). The screen imports `thyroid-panel.csv` and correctly reads TSH
4.82, TPO antibodies 212 and Vitamin D 21 — then flags all three because the CSV's own last column
says `HIGH`, `HIGH`, `LOW`.

**The screen's question is "did we read this right", not "is this result normal".** The canvas is
unambiguous about it: every flag reason in `CEPKc` is about our confidence in the parse —

- *"No unit in the file"*
- *"Converted from ng/mL"* → *"Check the maths"*
- *"Read day-first"* → *"Confirm the date"*

— and a row we are sure about reads *"Matches"*. Not one of them is about the value being out of
range.

**Why this is worse than a cosmetic mix-up.** The primary action says *"Fix the 3 flagged"*. Shown
against a genuinely high TSH, that invites someone to edit a real clinical result because the
interface implied it was our mistake. An import review that encourages correcting the lab is doing
the opposite of its job — and this product shares the *readings*, not the file, so an edited value
is what a clinician would later receive.

## What to build
- Flag on **parse uncertainty only**: a missing unit, a converted unit, an ambiguous date, an
  unrecognised marker name, a value we could not place in its reference range.
- A lab's own H/L/HIGH/LOW column is **data to carry, not a flag to raise**. It belongs in the
  record — a clinician reading the panel wants to know the lab called it high — and it belongs
  nowhere near "needs a look".
- If a row is read cleanly *and* abnormal, it reads **"Matches"**, like any other clean row.
- `lib/import.ts` is where the flag is decided; the screen only renders it. Check whether the same
  conflation reached `lib/archive.ts`'s record shape, and whether `verify:deident` or
  `verify:archive` assert anything that depends on it.

## Also
The demo dataset in `DESIGN.md` fixes **3 flagged of 32** at import. The fixture currently yields 3
of 10 by coincidence of it having three out-of-range values — so the numbers agreeing today proves
nothing. Once flags mean parse uncertainty, make the fixture produce the dataset's figures on
purpose, or say plainly in the story that the demo dataset and the fixtures are different things.
