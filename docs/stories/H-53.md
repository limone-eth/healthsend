# H-53 — One upload, many grants: split the asset from the sharing

## Story
- `createSend` uploads on every send. Separate the encrypted asset from grant issuance, so a
  blood-test PDF is uploaded once and shared as many times as the sender likes.

## Context
Tasks 4 and 5 of the TACo PoC plan, and the code half of `DESIGN.md` § *Upload once, bundle per
share*. Depends on H-50, H-51, H-52.

This is the same model H-44 landed for the archive, applied to the send path.

## What to build
- `lib/assets.ts` — `EncryptedAsset`, `createEncryptedAsset`: pack, encrypt and upload **one**
  reusable in-memory asset.
- `lib/sends.ts` — `createThresholdSend`: issue a grant against an existing asset, with a
  **different link share per grant** for the same content key. v3 opening in `openSend`,
  preserving the v1 and v2 paths exactly.
- `app/s/[key]/page.tsx` — v3 handling inside the existing `OpenedSend | OpenFailure` results. The
  six resolutions and their copy do not change.

**Memory only.** The content key, the released share, the link secret, the unwrapped message kit
and the plaintext must never reach localStorage, sessionStorage, IndexedDB, Cache Storage, cookies,
logs or a database. A refresh of the sender's tab discards the asset key and ends grant creation
from that session — deliberate for the PoC, and a real product gap to record in `## Choices`.

## Evidence
The acceptance proof the spec names: one Swarm upload, two grants, two deadlines. Keep one
recipient from obtaining any key material before the first deadline; afterwards its **untouched**
original link must not open, while the second grant still opens **from the same Swarm reference**.
Then show that previously acquired keys still work — that is the honest half of the promise.

## Non-goals
- Per-file, per-marker or per-date encryption inside the asset.
- Durable owner-key recovery or cross-device resharing after a refresh.
