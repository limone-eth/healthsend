# H-33 — Three failure modes are reported to the reader as expiry
## Story
- An Arkiv RPC returning 404, and a malformed but live entity, both reach the reader as *"This link
  has expired."* A rejected holder fetch reaches them as a decryption error. All three are our
  infrastructure failing, and the product's central distinction says so.

## Context
From the adversarial review: two high, one medium, all verified.

`README.md` § *The cost, stated plainly* is explicit — a broken holder *"must read 'temporarily
unavailable' and never 'expired'"* — and `healthsend.pen` Sheet 0 now carries it as a written rule:
*"Unavailable is never dressed as expired."* The seventh chip exists for this.

The gap is in classification, not in the pages. `lib/arkiv.ts`'s `isNotFound()` decides "gone" by
**matching substrings of an error message**, so a transport 404 from the RPC host — a wrong URL, a
proxy, a provider error page — is indistinguishable from a pruned entity. That heuristic was
already noted during the H-11 fold as something to keep mutations away from; this is the other half
of the same weakness.

## What to build
Classify on something structural rather than on message text: the RPC's own error shape, an HTTP
status distinguished from a JSON-RPC result, a live entity that fails to parse treated as an error
rather than an absence. When the code cannot tell, it must say it cannot tell — *unavailable* is
the honest answer to ambiguity, because it is the one that does not assert the sender's intention.

Add each case to the offline browser lane, which H-25 built for exactly this.

## Choices
- Classified "gone" on `error instanceof NoEntityFoundError` (from `@arkiv-network/sdk`), the SDK's
  own signal that a query round-tripped and returned zero rows. Everything else thrown by
  `getGrant` — an HTTP status from a wrong RPC URL or proxy, a `QueryError` the node itself
  rejected, a timeout — is structurally not that error, so it propagates instead of being
  swallowed to `null`.
- A live entity whose payload will not parse now throws a new `MalformedGrantError` (`lib/arkiv.ts`)
  instead of `toGrant` returning `null`. `getGrant` lets it propagate; `listGrants` (the sender's
  dashboard) catches it per-row so one corrupt entry does not fail the whole list — that filtering
  behaviour was not named in the brief, but nothing asked to change the dashboard, and the review
  finding was scoped to the recipient path (`getGrant`), not the list query.
- `openSend` (`lib/sends.ts`) routes a `MalformedGrantError` to `status: "error"` (a concrete,
  nameable defect) and every other `getGrant` failure to `status: "unavailable"`. The brief did not
  say which of the two existing states a transport failure should render as. I chose `unavailable`
  because the `"error"` screen's own copy states "the grant was found" — which would be false for a
  transport failure we never confirmed reached Arkiv at all — while the `unavailable` copy ("not
  expired... could not be reached... try again") stays true regardless of what actually happened
  upstream. Confidence 75 — sound, not needs-user, since no other reading keeps the existing copy
  honest, but this is the one call in this story an operator might weigh differently.
- Added `mockArkiv`'s `transport-fail` (HTTP 404, not JSON-RPC, for any method) and `malformed`
  (a live row whose payload is not JSON) scenarios, and a new `mockHolderUnreachable` helper
  (`route.abort("failed")`, reproducing a `fetch` rejection) to `e2e/helpers/network.ts`. Not
  prescribed by the brief beyond "each case gets a test in the offline lane" — these are the
  fixtures needed to reach each of the three failure modes without touching a real network.
- Each of the three new tests (`e2e/recipient.spec.ts`, "infrastructure failures are never dressed
  up as expiry") was run against the pre-fix `lib/arkiv.ts`/`lib/sends.ts` first — `git checkout --
  lib/arkiv.ts lib/sends.ts`, `playwright test --grep "infrastructure failures"` — and all three
  failed red (element not found: "Temporarily unavailable" / "Could not open this send") before the
  fix was reapplied with `git apply` and the suite went green.
