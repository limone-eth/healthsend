# H-33 — Three failure modes are reported to the reader as expiry
## Story
- An Arkiv RPC returning 404, and a malformed but live entity, both reach the reader as *"This link
  has expired."* A rejected holder fetch reaches them as a decryption error. All three are our
  infrastructure failing, and the product's central distinction says so.

## Context
From the adversarial review: two high, one medium, all verified.

`README.md` § *The cost, stated plainly* is explicit — a broken holder *"must read 'temporarily
unavailable' and never 'expired'"* — and `healthsend.pen` Sheet 0 now carries it as a written rule:
*"Unavailable is never dressed as expired."* The seventh chip exists for this.

The gap is in classification, not in the pages. `lib/arkiv.ts`'s `isNotFound()` decides "gone" by
**matching substrings of an error message**, so a transport 404 from the RPC host — a wrong URL, a
proxy, a provider error page — is indistinguishable from a pruned entity. That heuristic was
already noted during the H-11 fold as something to keep mutations away from; this is the other half
of the same weakness.

## What to build
Classify on something structural rather than on message text: the RPC's own error shape, an HTTP
status distinguished from a JSON-RPC result, a live entity that fails to parse treated as an error
rather than an absence. When the code cannot tell, it must say it cannot tell — *unavailable* is
the honest answer to ambiguity, because it is the one that does not assert the sender's intention.

Add each case to the offline browser lane, which H-25 built for exactly this.
