# H-40 — The app has a dark theme the design never had

## Story
- HealthSend is drawn as a light product. The running app renders a dark palette to anyone whose OS
  is set to dark — one that exists in no frame, was never designed, and makes every screen
  impossible to check against the canvas.

## Context
Raised by the operator on 2026-09-12: *"why is the design not using the same colors as on Pen?"*

Three things, each verified:

1. **`DESIGN.md` defines no dark palette.** No `prefers-color-scheme`, no dark tokens, no theme
   axis. The frontmatter is one light palette — `canvas #FBFBFB`, `surface #FFFFFF`, `ink #15161A`.
2. **No frame in `healthsend.pen` is dark-themed.** 3.4 *After it ends* uses the `grad-focus`
   gradient and is deliberately inverted — *"the one page that inverts"* — but that is a **dark
   surface inside a light product**, which is a different thing from a dark theme.
3. **The dark block came from the Next.js starter.** `git log --diff-filter=A app/globals.css`
   points at *"Initial commit from Create Next App"*, carrying `--background: #0a0a0a;
   --foreground: #ededed`. Scaffolding, never a decision.

**How it survived.** The H-1 brief said *"Light and dark are both defined at token level…
`app/globals.css` already has a working `prefers-color-scheme` block; that capability must
survive."* That instruction treated starter boilerplate as a requirement. H-1 kept it, which
produced the half-flipped palette of H-27 — and H-27 then did exactly as asked and **invented a
complete 23-token dark palette**, a second visual design nobody drew, reviewed, or asked for.

Both workers did what their briefs said. The briefs were wrong, and they were mine.

## What to build
- **Commit to the canvas's single light palette.** Remove the `prefers-color-scheme: dark` block
  and the invented dark values from `app/globals.css`. Set `color-scheme: light` on the root so the
  browser stops darkening form controls and scrollbars underneath us.
- Paint `background` and `color` explicitly on `body` from tokens. A page that commits to one
  visual world must still hold on a host that composites it over a dark ground.
- **Keep the designed dark surfaces.** `grad-focus`, `panel-on-dark`, `hairline-on-dark` and the
  3.4 inversion are part of the light design and must not be swept up with the theme.
- Delete the five legacy starter tokens (`--background`, `--foreground`, `--line`, `--accent`,
  `--surface` in their pre-H-1 form) once nothing imports them.
- **Repoint the contrast guard, do not delete it.** `e2e/dark-mode.spec.ts` catches a foreground and
  background resolving to the same colour, which is worth keeping — it just has to run against the
  light palette now. Rename it accordingly.

## Worth saying plainly
Roughly half of users browse with the OS in dark mode, so "no dark theme" is a real product
decision rather than a tidy-up. But it is the decision the design already made, and a dark theme
that no frame specifies is not an improvement on it — it is an unreviewed second design competing
with the one that was drawn. If a dark theme is wanted, it belongs on the canvas first.
