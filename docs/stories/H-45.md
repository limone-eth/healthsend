# H-45 — Two more ways the holder hands back what it should not

## Story
- Revocation is still not final, and a share signature still does not say what it is signing for.

## Context
From review 2, both with direct probe evidence.

**R2-002 — critical — unlock can return a share after revoke succeeds.** H-29 added a second
`getShare` before logging, which closed review 1's pre-check race. The best-effort log call opens
another window after that read. Probe: `{"revoked":{"ok":true},"shareAfterRevoke":null,
"unlock":{"ok":true,"share":"held-share"}}` — the revoke reported success, storage held nothing,
and the unlock still returned the share. `lib/unlock.ts:139`.

This is the same defect class as the one review 1 found, one layer further in. A third read would
open a fourth window; the shape of the fix is an **atomic read-or-refuse**, not another check.

**R2-005 — high — share signatures do not bind the stored payload.** `shareMessage` signs the
action, entity key and timestamp, and nothing else. Probe: capture one valid signature, then alter
`share`, `commitment` and `ttlSeconds` before first use; the holder accepted
`attacker-selected-share`, an attacker-chosen commitment, and a **one-year** TTL, and consumed the
write-once slot. `lib/share.ts:20`.

**R2-012 — medium — a complete Redis outage produces a confident zero-open log.** A read failure
renders as "nobody has opened this", which is a claim about the recipient's behaviour drawn from
our own infrastructure being down. `lib/holder-store.ts:246`.

**R2-015 — medium — revoke erases prior open counts shown in history.** Ending a share destroys
the record of who had already opened it. `lib/holder-store.ts:119`.

## What to build
- Make the unlock read-and-serve atomic with respect to revoke. One Lua invocation that returns
  the share **only if** no tombstone exists, with no window between the check and the return.
- Bind the payload into the signed message: the share, the commitment and the requested TTL.
  Keep the action namespace (`share`) — that property is already covered and must not regress.
- A holder read failure must be distinguishable from an empty log, all the way to the screen.
  "We could not reach the log" is not "nobody opened it".
- Access history must survive the revoke that ends access.

## Evidence
Each of the four probes above, as a test that **fails before the fix**. Say in the report which
line you broke to see it red. `scripts/revoke-proof.mjs` and `scripts/access-log-proof.mjs` are
the right homes; they already run the real Lua under fengari, so a fix that only works in a
JavaScript reimplementation will not pass.
