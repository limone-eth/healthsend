# H-62 — PDFs: upload several once, share any of them later

## Story
- Add one or more PDFs to your archive in a single step. Any day later, open New share, tick one or
  more of those PDFs, set a deadline, get one link. The person opening it sees the actual PDFs.

## Operator decisions, 2026-09-12
- **Scope is PDFs only** for now — blood test reports and similar documents. Other kinds (CSV marker
  tables, wearable exports) keep working as they are but get no new work here.
- **Select one or more at upload, and one or more at share time.**
- **The recipient sees the actual PDF**, exactly as issued — not extracted text. This deliberately
  reverses H-36's behaviour *for PDFs*, which sends cleaned text. The consequence is stated below and
  is not optional.

## What is true today
- `/add` accepts one CSV or JSON file, and says the file "stays in this browser". There is no PDF path.
- `lib/archive.ts` has only `blood-panel` and `wearable-series` record kinds — no document kind.
- New share accepts multiple files including `.pdf`, but H-36 converts a PDF to cleaned `text/plain`
  before sending, so the recipient never receives a PDF.
- The recipient's `PdfPreview` (Blob pinned to `application/pdf`, bytes checked for `%PDF-`, iframe
  deliberately unsandboxed) exists and is correct — it is simply no longer reached by sends.

## What to build
- **A document record kind** in the archive holding the encrypted PDF bytes plus its display name,
  size and added date. Stored through `lib/archive-store.ts` like the existing kinds.
- **Add: pick one or more PDFs at once.** `multiple`, `accept="application/pdf,.pdf"`, verify `%PDF-`
  on the way in and reject anything that is not a PDF. Replace "stays in this browser" copy with what
  actually happens.
- **New share: list archived PDFs with multi-select.** The operator's example: *"Blood test, March and
  Thyroid panel, June — 2 of your 12 documents"*. Empty archive → say so and route to Add.
- **Share from selections.** A send path taking the selected archive documents: read them with the
  archive key, pack the chosen PDFs into the existing multi-document envelope, seal under a **fresh
  share key**, upload that one sealed bundle, split the share key, write the grant. The archive key is
  never split, never sent. **No upload of the source PDFs at share time** — assert exactly one blob is
  uploaded per share, and it is the sealed bundle.
- **Recipient:** the bundle opens in the existing multi-document switcher with each PDF rendered by
  `PdfPreview`. Do not weaken the `application/pdf` pinning or the `%PDF-` check.

## The consequence that must be said — identifiers travel inside a PDF
Sending the real PDF means the name and date of birth printed on it go to the recipient. This product
has been caught six times making claims about personal data the build did not honour. So, as part of
this story, **every claim that identifiers are removed must be made true for PDFs or corrected**:
- `app/landing/page.tsx` STEPS[0] — says name and date of birth are set aside.
- `app/(sender)/page.tsx` Identity inset — says they "stay with you".
- `components/demo-notice.tsx`.
- `DESIGN.md` and `README.md` wherever they state it.
The honest statement for PDFs: *the document is shared as issued, including any name or date of birth
printed on it.* Say it on the share screen before the link is created, not only in docs.

## Evidence
In a browser, with a reload in the middle: add two PDFs in one pick, **reload**, open New share, tick
one, create the link, open it in a clean context, see that PDF render. Share the *other* PDF to a
second link from the same archive and show neither source was uploaded again. A component-state test
proves nothing here.

## Non-goals
- Removing names from inside PDFs (redaction). Deliberately not chosen.
- Per-document keys or per-document deadlines inside one link. The bundle stays the unit of expiry.
- The TACo release path (H-52–H-55) — this story uses the existing holder.
