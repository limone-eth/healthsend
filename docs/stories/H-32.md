# H-32 — The access log is best-effort, and its TTL can fail open
## Story
- A served unlock can leave no record, so *"Not opened yet"* can be shown about a share that was
  opened. And a log whose `EXPIRE` fails keeps a sender's access timestamps with no expiry at all.

## Context
From the adversarial review, two findings rated high (confidence 100 and 99).

**No record.** `lib/unlock.ts:105` catches a log-write failure and serves the share anyway. That was
briefed — *"recording must not be able to fail the unlock"* — and the reasoning stands: a reader's
access should not depend on our bookkeeping. But the consequence was not thought through. The
sender is shown a state derived from the log, so a dropped write does not degrade the log, it
**misinforms the sender**, and `verify:log` currently asserts this as correct behaviour.

**No TTL.** `lib/holder-store.ts:102` writes `RPUSH` then `EXPIRE` as two operations. The reviewer's
probe accepted the first and rejected the second: the timestamps persist without a TTL. `DESIGN.md`
and the H-12 brief both say the log expires with the share, precisely so it is part of the
arrangement rather than a permanent record of someone's reading habits. This is the one property
that most needs to hold.

## Added after H-29 (2026-09-12)

The same non-atomic pattern now guards a **security** property, not only the log. `tombstoneShare`
issues three operations in a `Promise.all`:

```
del(share)  ·  del(accessLog)  ·  set(tombstone, ex: ttl)
```

If the delete succeeds and the tombstone write fails, the slot is free with nothing marking it
revoked — and the hole H-29 closed reopens for that share. `putShare`'s guard is also a read
(`isRevoked`) followed by a separate `set`, so a revoke landing between the two can let a write
through.

Both are narrow races on a healthy Redis, and both are the same defect as the log's `RPUSH`-then-
`EXPIRE`: a multi-key invariant expressed as independent operations. Whatever makes the log atomic
should make this atomic too — solve it once.

## What to build
- Make the TTL atomic with the write, or set it on a key that cannot exist without one.
- Decide what the sender sees when a write was dropped, and say it. *"Not opened yet"* must not be
  shown when we do not know — the same expired-versus-unavailable distinction this product already
  makes on the recipient side, applied to the sender's.
- Update `verify:log` so it asserts the decided behaviour rather than the current one.

## Also
The same review found the access-log proof **does not connect writes to reads** — the read test
builds its own `opened` array rather than reading what the write test stored, so a writer that
stored the wrong key would still pass. That is H-34.

## Choices

**Mechanism: `eval()`, not pipeline/multi.** `@upstash/redis` is an HTTP client with no
`MULTI`/`EXEC`. `.pipeline()` (`.multi()` is the same thing under another name) is documented by
the client itself as non-atomic — commands from other clients can interleave with it. `eval()`
(Lua) is the one primitive that runs as a single, indivisible operation server-side. All three
multi-key writes (`recordAccess`, `tombstoneShare`, `putShare`) now go through one of three Lua
scripts in `lib/holder-store.ts` — one mechanism for all three, as asked.

**Red before green.** Three throwaway scripts (not committed) modelled the pre-fix code against a
tiny fake store and proved each defect before the fix removed it:
- Old `recordAccess` (`RPUSH` then `EXPIRE` as two calls): with the first call succeeding and the
  second failing, the fake showed a list holding an entry with no TTL — the exact defect. Against
  the new `recordAccessWith` (one `eval`), `scripts/access-log-proof.mjs`'s "a rejected EXPIRE must
  not leave a list without a TTL" case is green: a failed call appends nothing, and an
  already-written entry keeps its TTL.
- Old `tombstoneShare` (`Promise.all` of `del(share)`, `del(log)`, `set(tombstone)`): with the
  tombstone write failing, the fake showed the share deleted and no tombstone present — a free,
  refillable slot, reopening H-29's hole. Against the new `tombstoneShareWith` (one `eval`), "a
  failed tombstone write must not leave a refillable slot" is green: a failed call touches nothing,
  and the share (not a free slot) is what survives.
- The "reliable" field on the access-log read did not exist before this story, so there is no
  prior code to fail against — its red state is the absence of the field itself: every empty log
  used to read as a confident "never opened" regardless of whether a write had been dropped.

**Where the new atomicity tests live.** The brief's lane counts fix `verify:revoke` at 11 and mark
only `verify:log` "(grown)". The tombstone/putShare atomicity cases test `lib/holder-store.ts`
directly (the shared mechanism), not `lib/revoke.ts`'s signature/authorisation logic that
`revoke-proof.mjs` already covers — so all three new atomicity cases, plus the "reliable" cases,
were added to `scripts/access-log-proof.mjs` instead, keeping `verify:revoke` unchanged at 11 PASS
lines.

**What "the sender is told" means here.** `lib/access-log.ts`'s `readAccessLog` now returns
`reliable: boolean` alongside `opened`. `reliable: false` means a write for this entity is known to
have been dropped, so an empty or short `opened` must not be read as a confident zero. No UI reads
this yet (H-10 is out of scope here, per the brief's non-goals) — this story decides the signal and
its meaning; H-10 is expected to map `reliable: false` onto the existing `unavailable` chip state
(`DESIGN.md` § Share state chip), the same "we don't know" vocabulary the recipient side already
uses, rather than inventing an eighth chip.

**The degraded marker does not self-clear.** Once a write for an entity is known to have been
dropped, `reliable` stays false for that entity until the marker's own TTL lapses (pinned to the
same window as the log's own write), even if a later unlock records cleanly. A later clean write
does not prove no *earlier* event went missing, so clearing on success would let one recorded open
paper over an unrecorded one. This is the conservative reading of "say so when we don't know" —
confidence 70, `sound`, but a reasonable alternative (clear on next clean write) exists and was not
directly specified by the brief.

**Degraded marker is itself best-effort, not atomic with the log write.** Marking degraded happens
as a second, independent `SET` after the primary `eval()` fails — it is not folded into the same
atomic script, because if the primary call could not reach Redis at all, a second call to the same
Redis is not guaranteed to succeed either, and there is no way to make "tell the reader we failed"
atomic with the failure itself. If the marker write also fails, there is no further fallback:
`recordAccessWith` still rethrows, and `lib/unlock.ts`'s existing swallow is the last line of
defense — the reader's access is unaffected, and the sender is left with a log that reads as
reliable when it was not. This is a known, accepted gap on the rarer double-failure path, not a
silent one — confidence 65, `sound`.
