# Threshold alternatives for Healthsend expiry

Researched 2026-09-12 against official documentation and upstream code. Architecture proposals below are not implemented or tested against a deployed cohort. Read alongside the requested Desktop expiry scenarios, particularly section 10, and the vendored ETHRome manual.

## Finding

**TACo is the strongest verified protocol fit, but not a verified deploy-now network.** Its current SDK landing page says there is no stable operator cohort or supporting infrastructure, and describes the documentation as an open-source reference pending a WEDF relaunch planned for Q3 2026. The homepage and WEDF project page corroborate that future relaunch. Being in Q3 does not establish that it has happened. The current testnet page expressly says that active infrastructure is unavailable, including testnets. A prototype therefore requires separately verified working infrastructure or a deliberately operated development cohort. [Current testnet warning](https://docs.taco.build/for-developers/quickstart-testnet/get-started-with-tac). [Current SDK status](https://docs.taco.build/for-developers/taco-sdk), [current homepage](https://docs.taco.build/), [WEDF relaunch](https://worldethicaldata.org/projects/taco). Its `JsonRpcCondition` can directly query arbitrary HTTPS JSON-RPC endpoints, including Arkiv's nonstandard methods. It is distinct from the much narrower `RpcCondition`. Current Lit documentation presents both an older threshold SDK model and Chipotle, whose encryption uses a TEE-derived symmetric key. Chipotle can implement the gate, but should be described as a programmable enclave service rather than automatically as an independent threshold committee. [TACo JSON-RPC condition](https://docs.taco.build/for-developers/taco-sdk/references/conditions/json-endpoint-conditions/jsonrpccondition), [Lit encryption comparison](https://developer.litprotocol.com/lit-actions/migration/encryption).

Neither design makes previously delivered keys or plaintext expire. What expires is the ability to obtain *new* decryption assistance. Stored threshold ciphertext remains attackable if the network's secret material is compromised later; this replaces deletion of a per-share holder record with continued cryptographic/policy protection.

## TACo: verified capabilities and practical limits

- **Arbitrary Arkiv RPC is plausible without a Healthsend proxy.** `JsonRpcCondition` specifies an HTTPS `endpoint`, arbitrary `method`, `params`, and a JSONPath `query` relative to the response's `result`. It sends JSON-RPC 2.0 via POST. Bad HTTP responses, missing JSONPath matches, and JSON-RPC errors fail closed. The implementation has a five-second HTTP timeout. This is not an Arkiv integration test. [Official condition docs](https://docs.taco.build/for-developers/taco-sdk/references/conditions/json-endpoint-conditions/jsonrpccondition), [RPC implementation](https://github.com/nucypher/nucypher/blob/fbec7ec2fe7e089f63f7a6fa475ddff6dc0da0d7/nucypher/policy/conditions/json/rpc.py), [HTTP implementation](https://github.com/nucypher/nucypher/blob/fbec7ec2fe7e089f63f7a6fa475ddff6dc0da0d7/nucypher/policy/conditions/json/base.py).
- **Do not substitute `RpcCondition`.** Its upstream `RPCCall.ALLOWED_METHODS` currently contains only `eth_getBalance`; its provider manager also chooses configured supported chains. The JSON endpoint implementation instead takes a URL and has no EVM `chain` field or Ethereum-method whitelist. [EVM implementation](https://github.com/nucypher/nucypher/blob/fbec7ec2fe7e089f63f7a6fa475ddff6dc0da0d7/nucypher/policy/conditions/evm.py), [JSON implementation](https://github.com/nucypher/nucypher/blob/fbec7ec2fe7e089f63f7a6fa475ddff6dc0da0d7/nucypher/policy/conditions/json/rpc.py).
- **Policy is attached during encryption.** The SDK passes the condition into `encryptForDkg`, uses its authenticated data to build `AccessControlPolicy`, and includes an encryptor signature over the ciphertext header. The capsule must be encrypted with the *specific grant's* policy; accepting an unrelated live entity supplied during decryption would undermine expiry. [Pinned SDK source](https://github.com/nucypher/taco-web/blob/deacead89e121d79947abdfa0704bcfba719bcfd/packages/taco/src/taco.ts).
- **Recipient wallet is avoidable.** `decrypt` accepts a read-only ethers `Provider`; its context is optional. The decryption implementation generates ephemeral session transport keys internally. A condition referencing only a fixed public entity need not ask a user to connect or sign with a wallet. Encryption does require an encryptor signer. Source supports this API-level conclusion; browser integration remains to be tested. [SDK source](https://github.com/nucypher/taco-web/blob/deacead89e121d79947abdfa0704bcfba719bcfd/packages/taco/src/taco.ts), [decryption transport](https://github.com/nucypher/taco-web/blob/deacead89e121d79947abdfa0704bcfba719bcfd/packages/taco/src/tdec.ts).
- **RPC trust remains.** A fixed HTTPS endpoint is an oracle: threshold agreement does not help if every node queries the same compromised or stale RPC. Endpoints are embedded in immutable conditions. Independent endpoints and a fail-closed quorum policy improve this, but the exact combination and head-freshness checks need a spike. Do not let a recipient choose the endpoint, entity, historical block, or success value. [TACo endpoint considerations](https://docs.taco.build/for-developers/taco-sdk/references/conditions/json-endpoint-conditions).
- **Current network availability is a blocker to assuming managed deployment.** The latest SDK page explicitly warns that TACo lacks a stable cohort and infrastructure such as Porter; the current testnet page explicitly includes testnets in the unavailable infrastructure. WEDF plans a Q3 2026 relaunch. [Current testnet status](https://docs.taco.build/for-developers/quickstart-testnet/get-started-with-tac). JSON-RPC support exists in upstream code, but that does not establish a functioning service. Earlier indexed pages describe `tapir` ritual 6 (3-of-5) and paid mainnet cohorts with minimum 30 nodes, 12 months, and 100 encryptor credits. Treat those as historical onboarding information, superseded for availability purposes by the current warning; do not assume those offerings or commercial terms remain actionable. Even the old docs reject testnets for sensitive production data. [Current SDK warning](https://docs.taco.build/for-developers/taco-sdk), [WEDF status](https://worldethicaldata.org/projects/taco), [merged implementation](https://github.com/nucypher/nucypher/pull/3571), [historical testnets](https://docs.taco.build/for-developers/taco-integration/get-started-with-tac), [historical mainnet access](https://docs.taco.build/migration-to-mainnet/mainnet-taco-beta-program).

## Proposed single-upload, many-grant design

This describes a protocol design, conditional on working threshold infrastructure; it is not a claim that the public TACo network is ready today. The user's constraint is **one original Swarm upload**, with new sharing grants written to Arkiv. No second Swarm upload is required for a capsule.

For original ciphertext `C = AEAD(CEK, archive)` on Swarm, create a random high-entropy secret `Sg` for each grant `g`:

1. `Lg = HKDF(Sg, "healthsend/link-share/v1")`.
2. `Hg = CEK XOR Lg`.
3. Threshold-encrypt `Hg` into capsule `Tg`, under a policy bound to the specific Arkiv grant's identity and live state.
4. Derive `Wg = HKDF(Sg, "healthsend/capsule-wrap/v1")`, using a separate derivation domain. Outer-encrypt `Tg` with `Wg` and an authenticated binding to the grant context; publish only that encrypted capsule in the Arkiv payload alongside the Swarm reference and public metadata.
5. Send `/share/<grant-id>#<Sg>`. The browser fetches the live grant, locally unwraps the capsule, obtains TACo's decryption assistance, recovers `Hg`, reconstructs the original `CEK`, and downloads/decrypts the original Swarm ciphertext.

These are application-design deductions using the verified primitives above. They need a precise envelope specification and tests before implementation.

**Why the outer capsule encryption matters:** if every threshold capsule is public and the condition is only “entity live,” a crawler can obtain every held share while entities are live, and combine those saved shares with links leaked later. Hiding the capsule behind the high-entropy fragment prevents that prefetch without requiring recipient identity. Holding the capsule itself in the fragment is another option, but makes the link larger. Neither outer wrapping nor placing the capsule in Arkiv publishes the raw held share: permanent ciphertext alone cannot satisfy TACo after expiry.

**Multiple grants do not create multiple copies of the archive.** Every grant reconstructs the same original CEK. A recipient who successfully opens any grant can retain that CEK and access this unchanged Swarm ciphertext forever; later expiry or revocation of other grants cannot undo that. If grants should expose different subsets, the original upload must contain independently encrypted units and a manifest. One AEAD-encrypted monolithic archive cannot support cryptographic subset sharing simply by changing grant metadata.

**Avoid circular identifiers.** If Arkiv assigns the entity key only after creation, create the grant first without a usable capsule, then update its payload with a capsule bound to that returned entity key. Alternatively bind a pre-generated, unique grant identifier and the expected owner in the threshold condition, with verified anti-substitution semantics. The former is simpler to reason about; neither adds a Swarm upload. This sequencing is a proposal pending the Arkiv entity-update contract.

## Lit: separate the products and trust models

Chipotle's public API supports plain HTTP invocation, action-local authentication, and arbitrary fetches; therefore an immutable action could read Arkiv and release a held share. Its encryption key is derived from a PKP inside a TEE. The current docs explicitly compare this with Naga's BLS threshold SDK and immutable access conditions. Do not reuse section 10's wording about JavaScript across a threshold node set to describe Chipotle. The comparison page still discusses both approaches; it does not establish retirement of Naga. I did not verify a live Naga/Datil deployment or its current support window. [Encryption models](https://developer.litprotocol.com/lit-actions/migration/encryption), [Lit architecture](https://developer.litprotocol.com/architecture/index).

Ciphertext can be stored publicly; an authorized action and PKP group determine access. Healthsend would have to bind the grant identity, ciphertext, expected owner, and capability commitment inside the authenticated encrypted envelope or equivalent immutable policy. A shared action that accepts arbitrary `ciphertext` and an independently supplied live `grantId` is insufficient. Also review every action allowed to use the same PKP: a second permissive decrypt action bypasses the intended gate. [Lit vault model](https://developer.litprotocol.com/lit-actions/secrets).

Walletless callers can invoke Chipotle with a restricted usage API key and an action that checks the link capability. The master account key must stay private; usage keys can be scoped to specific groups for clients. Service credits and read-path availability remain operational dependencies. Current docs identify the Chipotle endpoint and a separate development endpoint; this research did not perform funded calls or attest a running enclave. [Usage keys](https://developer.litprotocol.com/management/api_keys), [pricing](https://developer.litprotocol.com/management/pricing), [published endpoints](https://developer.litprotocol.com/management/crypto).

## Corrections to section 10

- TACo's arbitrary JSON-RPC claim is supported, specifically via `JsonRpcCondition`.
- The encrypted capsule can live permanently on Arkiv when it remains protected by threshold encryption and the link wrapper. It need not be carried entirely in the link.
- A threshold network does not make a low-entropy PIN safe automatically. Distributed rate limits or a separate authenticated, stateful attempt-authority would still be needed; verify that authority's response is bound to this grant and request rather than a reusable boolean.
- Remove the unverified universal latency estimate and “both free testnets/paid mainnets” simplification. TACo currently publishes a no-stable-cohort warning pending a WEDF relaunch; historical ritual IDs and onboarding pages do not prove current availability. Lit product variants have different operational and trust models.
- Expiry and early revocation require current-state evaluation. Never accept historical live-state proofs as present authorization, and never imply that a recipient's previously obtained key is destroyed.

### Arkiv policy details to carry into the spike

The parallel local SDK review found authoritative `entity.owner` and `entity.expiresAt` metadata, separate from application-authored attributes. Bind the expected owner and grant identity to those semantics, and validate the original deadline cap independently: if the owner extends an entity, a policy that checks existence alone can keep releasing shares. Disable permissionless extension. Read-only payload flags should not be mistaken for an immutable lifecycle, because extension, deletion, and transfer remain separate operations. See the local [SDK entity types](../../node_modules/@arkiv-network/sdk/src/types/entity.ts) and [flags](../../node_modules/@arkiv-network/sdk/src/entity/flags.ts); the overall architecture review covers the Arkiv references. These details reinforce the need to test expiry, extension, revocation, ownership transfer, and stale RPC responses independently.
