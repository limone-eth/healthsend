# H-69 — Make Chipotle the live key release for shares from the archive

## Story
- A share made from the archive keeps its second key half in Lit's Chipotle enclave instead of on our
  holder server, and the enclave hands it back only while the Arkiv grant is still live.

## Why
Operator decision, 2026-09-12: *"use Chipotle because it works today… Keep TACo built, but park that
code."* H-65 and H-67 built the Chipotle adapter against Lit's real API. Nothing uses it yet:
- `createSendFromArchive` and `createSend`, the only paths the UI calls, hand the held share to
  `/api/holder/share`.
- The v3 threshold path (`createThresholdSend`, and `openSend`'s `payload.v === 3` branch) is
  hardwired to `createTacoKeyReleaseProvider`.

The operator has an account, a `healthsend` group (id 1) with one wallet, and a usage key. Registering
the action CID is the operator's step and may not be done when this runs. Build it so the switch,
`NEXT_PUBLIC_CHIPOTLE_ENABLED`, is the only thing between this code and live.

**Say it plainly everywhere:** Chipotle is an enclave service run by Lit, a TEE-derived key. It is not
decentralised, not trustless, and not a threshold network.

## What to build
- **One provider-neutral factory** (e.g. `lib/key-release/index.ts`):
  - **Protecting:** returns the Chipotle provider when Chipotle is enabled and configured. TACo stays
    parked, so it is never chosen for new shares.
  - **Releasing:** chooses by the grant's own `payload.release.provider` descriptor, never by today's
    env. A share protected by one provider must always release through that same provider.
  - **Refusing:** a descriptor the build does not know fails closed, with a clear error.
  - `lib/sends.ts` depends on the factory, not on `createTacoKeyReleaseProvider`. Keep dependency
    injection so the offline proofs can pass a fake.
- **`openSend` v3 branch:** release through the factory. A `ChipotleUnavailableError` reads as
  `unavailable`, exactly as `TacoUnavailableError` does today. The one authoritative "expired" remains
  the head-boundary check.
- **`createSendFromArchive` with Chipotle enabled:**
  - Bind the grant to a pinned `expiresBlock` (`buildGrantBinding`; never a duration, see `CLAUDE.md`).
  - Protect the held share through the factory and write the v3 grant via `createThresholdGrant`.
  - Keep the owner/expiry mismatch refusal that `createThresholdSend` already has.
  - **No holder hand-off.**
  - With Chipotle disabled, today's holder path is unchanged. Prefer sharing code with
    `createThresholdSend` over a third copy.
- **The four-digit code (H-7)** is enforced by the holder: five tries, then lock. Chipotle has no such
  counter. So a share **with a code stays on the holder path** even when Chipotle is enabled, and only
  a code-less share goes through Chipotle. Record this under `## Choices` as provisional.
- **Ending a v3 share early:** there is no holder half to delete. Find what actually ends it:
  - The action checks the grant is live on Arkiv, so deleting the grant entity as its owner should
    make the enclave refuse. Implement that for v3 shares.
  - Prove the enclave refuses afterwards with a fake client offline.
  - If owner deletion isn't possible on Arkiv, say so and leave the End action off for v3 shares
    rather than showing one that does nothing.
- **Opens:** the access log lives in the holder, so v3 shares have none. Anywhere the UI states opens
  (Your shares, and H-18's "opened on" note), a v3 share must show nothing rather than "not opened".
- **`/api/holder` preflight:** a Chipotle send must not fail just because the holder is down.

## Evidence
- **Offline proofs, run red first** (dependency-injected like `scripts/archive-send-proof.mjs`):
  - an enabled archive send never calls `/api/holder/share` and writes `v: 3` with a Chipotle
    descriptor;
  - a TACo-descriptor grant still routes to TACo;
  - an unknown descriptor fails closed;
  - a coded share stays on the holder;
  - a disabled flag leaves today's behaviour byte-identical.
- **E2E:** the recipient opens a v3 Chipotle fixture through a mocked Chipotle endpoint.
- **Live:** `RUN_CHIPOTLE_LIVE_PROBE=1 pnpm verify:chipotle-adapter-live`, reporting the stage it
  reaches. Blocked at `single-action` because the action is not registered yet is an acceptable
  outcome; say so.
- `pnpm lint`, `pnpm build`, `pnpm exec tsc --noEmit`, `pnpm test` and every non-live `verify:*` lane
  pass.

## Review log

## Choices

- **Bundling `chipotle-action.js` for the browser.** The repo has no raw-text
  bundler loader configured, and the cache-miss retry (amendments) has to
  submit this source from client-side JS. Chose to generate
  `lib/key-release/chipotle-action-source.ts` — a plain TS module exporting
  the file's exact contents as a JSON-stringified constant — via a new
  `pnpm chipotle:generate-action-source` script, rather than a Next.js/
  Turbopack `?raw`-style import rule. This needs no build config, works
  identically for the browser bundle and for the Node `--experimental-
  strip-types` proofs, and `scripts/chipotle-adapter-proof.mjs` now asserts
  the generated constant stays byte-identical to `chipotle-action.js` on
  disk, so a hand-edit of one without the other fails loudly rather than
  drifting silently.
- **A coded share always stays on the holder path**, even with Chipotle
  enabled — dictated by the brief (H-7's five-try counter has no Chipotle
  equivalent), recorded here as asked and flagged provisional: if Chipotle
  ever grows an equivalent attempt counter, this exception should be
  revisited rather than assumed permanent.
- **`ProtectedKeyShare.provider`/`.domain` widened to `"taco" | "chipotle"`**
  in both `lib/key-release/types.ts` and `lib/arkiv.ts`'s duplicate, replacing
  H-67's `as unknown as` cast. A real Chipotle-protected v3 grant now has to
  type-check honestly as what it is, not lie about being a `"taco"` share to
  fit a union of one.
- **`lib/sends.ts` never imports `./key-release/chipotle` or `./key-release/
  taco` directly** — only `./key-release` (the factory). `createThresholdSend`
  (unused by any UI today, but exercised by `scripts/taco-unlock-proof.mjs`
  and `scripts/single-upload-grants-proof.mjs`) now protects through
  `selectProtectingProvider` too, not a second hardwired TACo call site — the
  brief's "depends on the factory, not on `createTacoKeyReleaseProvider`"
  reads as file-wide, and this keeps exactly one call site ever choosing a
  protecting provider. Doing so required renaming those two scripts'
  injected dependency key from `createTacoKeyReleaseProvider` to
  `selectProtectingProvider`/`selectReleasingProvider` — they are not on the
  "must stay unmodified" list (only send-path, archive-send and recipient
  tests are), and both still pass.
- **`createSendFromArchive`'s Chipotle branch and `createThresholdSend` share
  one private helper**, `protectAndWriteThresholdGrant` (bind → split → protect
  → write the v3 grant → the owner/expiry mismatch refusal), per the brief's
  "prefer sharing code... over a third copy."
- **`endSend` now reads the grant via `getGrant` before deciding how to end
  it** — a v3 grant deletes the Arkiv entity (`deleteGrant`, new in
  `lib/arkiv.ts`, wrapping the SDK's own `client.deleteEntity`); anything
  else keeps today's holder-revoke call, unchanged. This adds one Arkiv read
  to every "End access now," including for an ordinary v2 share, since there
  is no cheaper way to tell the two shapes apart without threading the
  grant's version through the confirm-sheet call site instead. A lookup
  failure falls through to the holder path rather than blocking the action.
- **The confirm-end sheet's copy no longer says "This deletes our half of the
  key"** — false for a v3 share, which has no holder half. Replaced with
  provider-neutral wording ("This ends the grant right away").
- **Opens display for a v3 share**: added `hasAccessLog: boolean` to
  `KnownShare` (`false` for `payload.v === 3`). The sender's `/shares` page
  never calls `/api/holder/access-log` for such an entry, its chip is
  computed from time-remaining alone (skipping the opened/not-opened states
  entirely), and its "When she looked" line renders empty rather than "Not
  opened yet." Chose not to remove the footer row itself for a v3 share — an
  empty sentence and a disabled button say nothing false, and a larger layout
  change felt like more churn than this story asked for.
- **`scripts/chipotle-live-probe.mjs`'s stage 5 now calls the same
  `invokeActionWithCacheMissRetry` the real adapter uses**, exported from
  `chipotle.ts` for this purpose, instead of a bare `client.invokeAction`. A
  cold action cache on the live account is exactly the failure the
  amendments describe, and the probe should prove the adapter's actual
  behavior, not a narrower stand-in that would report a false "FAILED" on a
  cache miss it never learned to expect.
- **e2e Chipotle wiring**: `playwright.config.ts`'s `webServer` now sets
  fixed, non-secret `NEXT_PUBLIC_CHIPOTLE_*` values (via a new shared
  `e2e/helpers/chipotle-test-config.ts`) so the one new recipient spec can
  drive the real `createHttpChipotleClient` against a new `mockChipotle`
  Playwright route stub. Scoped to this suite's own spawned dev server only
  (Playwright's `webServer.env`), never the wider shell — and releasing is
  chosen by the grant's own descriptor, never by this flag, so no other spec
  is affected by Chipotle reading as "enabled" on that server.
- **Scope: only `createSendFromArchive` gets a Chipotle branch, not
  `createSend`.** The story's title and "What to build" section both name
  "shares from the archive" specifically; the fresh-upload path is
  unmentioned there and untouched here.
