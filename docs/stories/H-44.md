# H-44 — The archive is never written and never read

## Story
- `lib/archive.ts` can create an archive, add records to it, open it and scope a slice out of it.
  Nothing in the product calls any of those four functions. Your archive is permanently empty, and
  every feature built on top of it is unreachable.

## Context
Found folding H-17 (2026-09-12), which built 2.1 *Your archive* correctly and then had nothing to
put in it. Its `## Choices` say so plainly, and the honest empty state it shipped is the right
response to the gap rather than a workaround for it.

A grep settles it. `createArchive`, `addArchiveRecords`, `openArchive` and `scopeArchive` are
imported by exactly two things: `scripts/archive-roundtrip.mjs` and `lib/archive-demo.ts`, which
is itself only imported by that script. `app/(sender)/page.tsx` imports the *types* and holds a
local, always-empty `Archive`. No app code has ever written a record or read one back.

`docs/archive-model.md` names the missing piece: *"A stored archive is one encrypted period chunk.
A later manifest can address several chunks. The manifest is outside this model."* Nothing has
since brought it inside.

**This is the fifth capability to land proven-but-unwired**, after End access now, the access log
(both H-31) and de-identification (H-36). It is the largest of them, because it is load-bearing:

- **H-17** — every bucket says "Nothing here yet", forever.
- **H-18** *Remove data* — has nothing to remove, which is why it is held.
- **H-19** *Wearables in detail* — has no series to chart.
- **H-14 / H-23** — scope selection has nothing to select from, so `scopeArchive` has no caller.
- **H-36** — de-identification runs at import, and import is the step that does not exist.
- **H-22** — the assistant is served scoped records, which is `scopeArchive`'s output.

A capability with a passing proof and no caller reads as *done* on the board. Six stories now
depend on one that is not.

## What to build
Persist an archive for a signed-in sender and read it back.

- **Write.** `/add` (and, after H-38, the import review's confirm) turns an uploaded document into
  `ArchiveRecord`s and calls `addArchiveRecords`. Store the encrypted chunk the way sends already
  store a payload — Swarm, under the sender's own key — so this introduces no new trust boundary
  and no new service.
- **Read.** `app/(sender)/page.tsx` loads the real archive on sign-in instead of holding an empty
  one. Keep its existing empty treatment for a genuinely empty archive; it is correct and must not
  become a spinner that never resolves.
- **Address it.** A manifest, or the simplest thing that finds a sender's chunk(s) from their
  identity alone. `docs/archive-model.md` deliberately left this open — close it there too, in the
  same change, rather than leaving the document describing a model the code has outgrown.
- **Do not widen the record model.** `BloodPanelRecord` and `WearableSeriesRecord` are what exist;
  Medications and Notes have no model and stay empty. Adding two speculative kinds to make a grid
  look full is the opposite of this story.

## Evidence
End-to-end, in a browser, not another round-trip script. `verify:archive` already proves the
pack/unpack maths and proves nothing about persistence. Add a record, reload the page, and see it.

## Also
`lib/archive-demo.ts` exists only to feed `scripts/archive-roundtrip.mjs`. Once real records can be
written, say plainly in `## Choices` whether it is still the proof's fixture or whether it has
become a temptation to seed the UI with — and if the latter, make it impossible to import from
`app/`.

**`lib/archive-demo.ts` hardcodes the conflation H-38 just removed.** `DEMO_BLOOD_PANEL` sets
`flaggedAtImport: true` on exactly its three out-of-range markers — LDL cholesterol, ALT,

**`/import-review`'s inset claims the file is kept.** It reads *"The file itself stays in your
archive so you can come back and compare. It is locked to you like your name is — no share can
ever include it..."* Nothing stores the file today, which is this story. Note that the sentence
promises the **file**, not the records — so decide deliberately whether this story keeps the
original document alongside the parsed records, or whether the copy is wrong and should say what
is actually kept. Do not leave it asserting the one thing it asserts today, which is neither.

## The model this closes — operator, 2026-09-12

> "It's important that the user uploads only once, and those things are then bundled customly
> inside shared links when created and authorized."

Written up as `DESIGN.md` § *Upload once, bundle per share*. It is not a new requirement so much
as the reason this story exists: without persistence there is nowhere for a single upload to
land, so every send re-uploads.

Two consequences that bear on **how** this is built, not just whether:

- **Import is the only write path**, and it is where identifiers are set aside (H-16 chose that
  ordering deliberately — a de-identification step on the way *out* is a filter, which is a
  weaker promise). So the archive is the thing `/add` and `/import-review` write into, and the
  send path must stop reading the disk.
- **A share is a scope over the archive, not a file list.** `scopeArchive` already produces
  exactly that and has no production caller. Wiring the read side is this story; wiring the send
  side to select records instead of files is H-36's, and the two meet at `lib/sends.ts`. Say in
  `## Choices` what shape you left `createSend` in so H-36 can finish it without re-deciding.
- **Re-sharing the same panel to a second person must cost nothing new**: same record, second
  scope, second grant, second expiry. If your storage design makes that expensive, it is the
  wrong design.
