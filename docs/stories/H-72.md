# H-72 — Bind the Chipotle release to the real grant

## Story
- Once a Chipotle share has ended or expired, nobody can get its key half back, whatever they kept.

## Why (review-8, `/Users/limone/.fleet/state/runs/review-8.findings.md`)

**F1 — CRITICAL.** The commitment check in `lib/key-release/chipotle-action.js` is circular:
- In `protect` mode the action encrypts only `payload`. The binding `{grantId, owner, expiresBlock, ref}` is not sealed into the Lit ciphertext.
- In `release` mode the caller supplies both the binding and the `commitment`, and the action checks one against the other. Any self-consistent input passes.
- The action then checks the *supplied* grant is live and decrypts *any* ciphertext.

The attack, for anyone who kept the link:
1. Read the v3 payload from calldata, which is permanent.
2. Unwrap the Chipotle envelope with the link secret.
3. Write their own live Arkiv entity, using `/api/fund` for gas.
4. Call the action with a matching commitment and the public usage key. It releases the held half.

Expiry and "End access now" stop nothing for them. The proof is `scripts/r8-f1-commitment-bypass-proof.mjs` in `/Users/limone/.fleet/wt/review-8`; copy it into this story's branch as a regression proof.

**F5 — MEDIUM.** In `endSend` (`lib/sends.ts`), a thrown `getGrant` falls through to the holder revoke. That revoke succeeds as a no-op for a v3 grant, so the UI says "ended" while the entity stays live.

**F2 — HIGH, contingent on unverified live behaviour.** `chipotle.ts` states as fact that Lit refuses inline `code` whose CID isn't the group's permitted action. The published spec doesn't say so.

**F2, live evidence gathered before this story:** on 2026-09-12, with the production usage key and before the action was registered, `POST /lit_action` with inline `code` returned `403 "The provided API key is not authorized to execute the specified action (QmR32N27HKyj2AkvMcfLdt6cgg8dguFVyJGsBdHPvunjbn/…)"`. So Lit did gate inline code by its CID for that key. Treat F2 as a documentation fix: say what was observed, not a guarantee.

**Operator decision, 2026-09-13:** Chipotle stays enabled in production while this is built. That makes the fix urgent. Keep the diff focused, and land F1 first.

**F6 — MEDIUM, follows from F1.** The end and expiry copy says a Chipotle share "can't open it any more". That is only true once F1 is fixed.

## What to build

1. **Seal the binding inside the Lit ciphertext.**
   - In `protect`: encrypt `JSON.stringify({ v: 1, binding: {grantId, owner, expiresBlock, ref}, payload })`, not bare `payload`.
   - In `release`:
     1. Decrypt first.
     2. Parse the sealed binding.
     3. Query Arkiv with the **sealed** binding: `app`, `kind`, `grant_id`, `$owner`, `$expiresAt`, and the `ref` if it is an attribute. If it isn't, compare against the entity payload's `ref`.
     4. Return the held half only if that exact entity is live and matches.
   - Caller-supplied binding fields may stay for backward compatibility, but must never decide anything. Refuse when they disagree with the sealed binding.
   - Do not return the plaintext payload before the liveness check passes.
   - Decide how to handle existing v3 ciphertexts that carry no sealed binding. Refuse them (fail closed) and say so under `## Choices`.
2. **Treat it as a new action.**
   - The source changes, so the CID changes.
   - Regenerate `lib/key-release/chipotle-action-source.ts` (`pnpm chipotle:generate-action-source`).
   - Print the new CID with `pnpm chipotle:print-cid`. **Do not register it.** The operator registers it with the account key and swaps it in the group; list that step for them.
   - Keep `NEXT_PUBLIC_CHIPOTLE_ENABLED` reads as they are.
3. **F5:** in `endSend`, if the grant read fails, return `{ status: "error" }` and never fall through to the holder path. After `deleteGrant` for a v3 grant, read back and report "ended" only once the entity is gone. Otherwise report an error the UI shows.
4. **F2:** remove the unproven guarantee from the `chipotle.ts` comments. State plainly that inline-`code` execution rules are Lit's, and are not verified by this app.
   - Keep the cache-miss retry. It submits the exact registered source, checked by CID.
   - In the README's "cost" section and `arkiv/evidence/chipotle-adapter-poc.md`, add one line: the usage key ships to browsers, so the account's safety depends on that key's scopes being execute-only for group 1.
5. **Copy (F6):** once 1–3 hold, the existing end and expiry copy is true again. Don't weaken it. Do add a test proving it is true for v3.

## Evidence
- **Red first:**
  - review-8's F1 proof, adapted as `scripts/chipotle-binding-proof.mjs`, fails on the current action ("FAIL-OPEN … reconstructed: true").

  - It also refuses a sealed binding whose grant is deleted or expired.
- **F5 proof:** a thrown `getGrant` during `endSend` returns an error. The delete read-back is checked.
- **Keep passing:** `verify:chipotle-adapter`, `verify:archive-send-chipotle`, `verify:end-v3-send`, `verify:key-release-factory`, and every other non-live lane, plus `pnpm test`.
- **Report:** the new CID and the operator's exact two registration steps.
