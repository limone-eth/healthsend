# H-7 — 3.1 First open: the code, and claim-on-first-open

## Story
- The design promises a four-digit code sent separately from the link, and a share that binds to
  the first phone that opens it. Neither exists: today the link alone is the whole credential.

## Decided 2026-09-12 — the code is OPTIONAL, and where it lives is the whole story

**Optional, chosen per send.** The compose screen offers it; a sender who does not want the friction
sends without one and nothing changes. H-8 already renders the slot for it, disabled. Making it
mandatory would tax every ordinary send to defend against a case the sender is best placed to judge.

### Where the code must NOT go

**Never into anything written to Arkiv.** `authCommitment` is public and permanent in the creating
transaction's calldata — `scripts/payload-survives.mjs` proves an expired grant's payload is still
recoverable, and `arkiv-encryption`'s own README states the same thing: *"Entity Expiration removes
active availability; it is not erasure of transaction history or other copies."*

So deriving the on-chain commitment from the code puts a **10,000-entry search space in permanent
public storage**. Anyone with the link grinds it offline in milliseconds, forever. That is worse
than no code at all, because the interface would claim a protection that does not exist.

The on-chain commitment stays exactly as it is: over the link secret alone.

### Where it goes instead — both places, for different reasons

**1. A verifier held only by the holder, rate-limited.** The holder refuses to serve its share
without proof of the code, counts attempts per entity key, and disappears at expiry. Four digits is
only safe behind a counter, and a counter needs a party that can refuse — which is the same reason
the holder exists at all.

**2. Mixed into the link half of the key**, so `linkShare = HKDF(linkSecret, code, "share/v2")`.
This is defence in depth against the holder itself: a compromised or compelled holder that serves
its share to the wrong person still hands over something useless, because the other half cannot be
derived without the code.

Neither alone is sufficient, and the reason is worth writing down. (1) alone fails if the holder is
compromised. (2) alone fails because an attacker holding the link can obtain the holder's share
legitimately — the auth key derives from the link secret — and then grind four digits offline
against the AES-GCM tag in microseconds. **Together**, an attacker with the link must guess the code
online, against a rate limit, to get anything at all.

### Consequences to handle
- A wrong code produces a wrong key, so decryption fails on the GCM tag rather than at a check. The
  reader must see *"that code isn't right"*, not a decryption error — `lib/sends.ts` already
  distinguishes statuses and this needs one more.
- A share made with a code cannot be opened without it, by anyone, including the sender. Say so at
  compose time.
- The code is sent **separately from the link**, which the design is already explicit about — 2.5
  says it travels on its own, away from the link, and 3.1 asks for it before anything renders.

### What this is not
It does not replace the holder, and it does not make expiry work without one. It closes a different
hole: a **leaked link alone stops being enough**. That is the genuinely good idea in the Arkiv
team's PIN proposal, adopted here without the part that would have removed expiry.

## Context
Depends on: H-1.
Design: `wIxCY` (desktop), `e1Zud2` (mobile). `DESIGN.md` § Words we use — say
*"Lock it to their phone the first time they open it"*, never "device binding".

**Read this before designing the crypto.** The obvious implementation is wrong. `authCommitment`
is written to Arkiv, which means it is public and permanent in the creating transaction's
calldata. Mixing a four-digit PIN into the value that gets committed there puts a 10,000-entry
search space in public, permanent storage — grindable offline in microseconds, by anyone, forever.

The PIN verifier must live **only in the holder row**, which can rate-limit and which disappears
at expiry. That is the same division of powers the architecture already rests on: the holder has
capability without authority, Arkiv has authority without capability. Keep the on-chain
commitment exactly as it is — over the link secret alone.

Then:

- Rate-limit per entity key at the holder. Four digits is only safe behind a counter.
- On first successful unlock, record the device claim. Later unlocks presenting a different claim
  are refused — that is the `On their device` state in the share table.
- The sender's copy on 2.5 says the code is sent on its own, away from the link. The compose flow
  must actually generate and show it, not imply it.

This is the most security-sensitive story on the board. It gets a design stage.

## Review log

## Choices

- **The helper line under the code boxes reads "They sent this", not the frame's "She sent
  this".** `wIxCY`/`e1Zud2`'s `H` node literally reads "She sent this on its own, away from the
  link — check your messages." — a gendered sender the frame assumes elsewhere too. This node
  predates H-47's de-gendering pass (nothing rendered 3.1 before this story, so there was nothing
  for that pass to touch), but the app's standing convention — established explicitly in
  `new/page.tsx` and its own `## Choices` for the same reason — is that neither party's gender is
  known, so no page states one. Copying "She" verbatim here would reintroduce a pronoun this
  codebase has already removed everywhere it renders. Every other string in both frames is copied
  exactly as read.
- **The compose-screen code toggle has no design node.** The story's "Context" section says "H-8
  already renders the slot, disabled — enable it", but H-8 never built a PIN control at all —
  `new/page.tsx`'s own file-level comment (pre-this-story) says the PIN and assistant controls
  "have no backing code path... and are left out rather than faked." There is nothing to enable.
  `ToggleRow` is a new component, built here, styled to match `AccessModeRow` immediately above it
  in the same panel rather than inventing a new visual language.
- **The code-required check is a second round trip to the holder, probed with an empty proof,
  rather than a flag carried on the grant.** `lib/arkiv.ts` is off-limits to this story, and
  `GrantPayload`'s shape is a strict type there — there is nowhere on-chain to say "this send has
  a code" without touching a file the brief forbids. The holder already knows (it stored the code
  guard), so the recipient's browser asks it first with no code, gets told whether one is needed,
  and only then shows 3.1's screen. An uncoded send — the overwhelming common case — takes exactly
  the one round trip it always did: `checkCode` returns `"none"` before ever reaching the
  attempt-rate-limit branch.
- **The code verifier and its rate limit are a new, separate atomic operation
  (`CHECK_CODE_SCRIPT`/`checkCode`), not a change to `SERVE_SHARE_SCRIPT`.** H-45 landed the same
  day this story was picked up and the brief is explicit: build on it, do not undo it. Folding the
  code check into the existing serve script would have meant changing a script three other proof
  scripts already exercise by exact text. A second script, checked immediately before the serve
  step, keeps H-45's script and its guarantees untouched and byte-identical.
- **Five wrong attempts locks a coded grant out for the rest of its life.** The story asks for
  "rate-limited" without a number. Five is a conventional PIN-lockout figure (bank cards use the
  same order of magnitude) against a 10,000-value space, and it is cheap to change later — the
  constant is `MAX_CODE_ATTEMPTS` in `lib/holder-store.ts`, read in exactly one place.
- **Both "a code is required" and "the code is wrong" and "locked out" share one HTTP status
  (401) with a distinguishing flag**, the same shape `lib/unlock.ts` already used for
  revoked-vs-expired on 410. Introducing a second status code (429 for "locked") would have meant
  a second parallel branch in `openSend` for a distinction the flag already carries.
- **The "Who can open it" row on 2.5 (Link ready) now reads "Anyone with the link and the code"
  when a code was added.** 2.5 is not one of this story's named frames, and its existing text
  ("Anyone with the link") was already a deliberate adaptation (see H-1's own choices on that
  screen). Leaving it unconditionally at "Anyone with the link" for a coded send would have been a
  false claim of exactly the kind `DESIGN.md`'s "Words we use" table exists to prevent ("say the
  risk in the sentence that offers the option").

## Correction — review 3, R3-016, decided 2026-09-12

**The security claim above was wrong, and the operator chose to keep the four-digit code and narrow
the claim rather than change the mechanism.**

The spec said the two defences together protect against a compromised holder. They do not. A
compromised holder releases `heldShare`; the link supplies the link secret; the attacker derives
all 10,000 candidate link shares, XORs each with `heldShare`, and tests against the GCM tag —
offline, never contacting the holder, so the rate limit never applies. Review 3 recovered code
`9999` and the plaintext in 534 ms.

**What the code honestly does:** someone who has *only* the link — forwarded, leaked, synced to the
wrong device — must guess online against the holder, which allows five attempts. That is real and it
covers the common case.

**What it does not do:** protect against someone holding both the link and the holder's share. No
four-digit secret can resist an offline search, so nothing may say or imply that it does.

The mechanism stays exactly as shipped. The on-chain commitment remains independent of the code.
