# H-37 — Three divergences between /add and the canvas, and an avatar on the tab bar

## Story
- `/add` reads four cards as *Later* where the canvas gives each a kind descriptor, the mobile tab
  bar uses the desktop's long labels, and the account avatar sits on top of the tab bar.

## Context
Found folding H-14 (2026-09-12) by extracting every string from frames `gxi6Y` and `TdVX6` and
comparing them against the build and its screenshots at 1440 and 400.

**1. The badge slot is a kind descriptor, not an availability flag. (H-14, and my fault.)**

The canvas gives each card a badge saying *what sort of input it is*:

| Card | Desktop badge | Mobile badge | Build shows |
|---|---|---|---|
| Lab or test result | A file | A file | A file ✓ |
| Wearable export | A file | A file | A file ✓ |
| Medications | **You type it** | You type it | Later ✗ |
| Your health history | **A questionnaire** | 10 minutes | Later ✗ |
| Notes | **You type it** | You type it | Later ✗ |
| A letter or report | Later | Later | Later ✓ |

Only one card is *Later* in the design. The H-14 brief told the worker to mark as *Later* anything
`lib/archive.ts` cannot model, and it followed that faithfully — so this is a brief defect, not a
worker defect.

The instruction was wrong on its own terms. Medications and Notes are *"You type it"* and health
history is a questionnaire: none of them needs a parser, which makes them **more** buildable than
the file kinds, not less. Conflating "the archive model has a record type for this" with "a person
can enter this" is what produced four greyed-out cards.

Restore the descriptors. Whether those three kinds are selectable yet is a separate question — if
they are not, the disabled state must not borrow the *Later* badge, which means something else.

**2. The mobile tab bar uses the wrong labels. (`components/chrome.tsx`, H-3.)**
`TdVX6` says **Archive · Shares · Assistant**. The build renders *Your archive · Your shares · Your
assistant*, the desktop rail's labels, which is why they crowd at 400px.

**3. The account avatar is rendered over the tab bar. (`components/chrome.tsx`, H-3.)**
At 400px the avatar circle sits in the bottom-left corner, overlapping the *Archive* tab's label.
The mobile frame has no avatar there at all — the tab bar is three items and nothing else. The rail's
footer is not part of the mobile chrome and should not render at that breakpoint.

**4. Content is not padded for the fixed tab bar. (`components/chrome.tsx`, H-3.)**
On `/import-review` at 400px the primary action *"Fix the 3 flagged"* renders **underneath** the
bottom bar and cannot be tapped. The tab bar is fixed and nothing reserves space for it, so the last
element of any page that fills the viewport is unreachable. This will hit every mobile screen, not
just this one — it is the chrome's bug, found on the second screen built against it.

## Not a divergence — checked and correct
The mobile copy is **abridged, and that is faithful**: `TdVX6` really does say *"The kind decides how
we read it and where it lands."* and *"A PDF or a photo"*, and the build matches verbatim. This is
the same systematic d/m abridgement found on the landing page, which is the subject of **H-26** —
and a second instance strengthens the case that `DESIGN.md`'s "content is identical" rule is what is
wrong, not the frames.
