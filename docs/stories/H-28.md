# H-28 — De-identification only catches labelled identifiers, and the page claims more

## Story
- `app/landing/page.tsx` says *"Your name and date of birth are set aside as they come in, so they
  are never part of anything you send."* H-16 made that true for documents that label their
  identifiers. A name in a letterhead, a `Re:` line, or a bare table cell still goes through.

## Context
Found while folding H-16 (2026-09-12). **This is a gap, not a defect** — H-16's work is sound and
strictly better than what came before. The problem is the distance between what it does and what
the product says it does.

`lib/deident.ts` matches four labelled patterns:

```
patient name | patient | name   :  …
date of birth | dob              :  …
address                          :  …
mrn | patient id | patient number | record # | record number : …
```

What it does well, and should be preserved: it strips the label **and** the value, then scrubs
every later recurrence of that value, matching on words rather than the literal so a PDF's fixed
line width cannot smuggle `Jane\nRivera` past a literal comparison. That detail is the difference
between a real scrub and a cosmetic one.

What it cannot see, because no label precedes it:
- a name in a letterhead or footer
- `Re: Jane Rivera` / `Patient, Jane (1984-03-02)`
- a name or DOB in a table cell whose header is two rows up
- an identifier in PDF metadata rather than a text run
- a second patient's name mentioned in a consult note

## Two things to decide, and they are separable

**1. Widen the detection.** Add unlabelled heuristics — a DOB-shaped date near the top of a
document, a name matching the sender's own account name wherever it appears, a configurable list
the sender confirms at import. Note that the import review screen (H-15) is the natural place for a
human to catch what a matcher misses, and that it is the honest design: *show the sender what we
took out and what we left*, rather than promising a machine caught everything.

**2. Make the claim match the code, today.** This is the more urgent half, and it is cheap. Right
now the landing page states the general claim while the implementation is bounded. Options:
either qualify the copy (and the canvas frame `xKspH`, node `IagoV`, which is the source), or keep
the general claim and treat H-28's detection work as the thing that earns it.

Whichever way it goes, **it must not sit as it is**: a claim about what happens to a name on a
health record is exactly the kind this repository has already had to retract once, and the retraction
is the most credible thing in the README.

## Also
`components/demo-notice.tsx` says *"nothing yet sets aside your name and date of birth before a
file is shared."* That is now wrong — something does, for labelled formats. Update it to say what
is actually true rather than deleting it, since the bounded version still warrants a warning.
