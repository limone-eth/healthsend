# H-61 — The growth hook invents an account

## Findings (review 3)
- **R3-009 (medium)** `app/s/[key]/page.tsx:171` — the growth hook says "the same account you used to
  open this", but a recipient opens a link with **no account at all** — that is the product's core
  recipient promise. It also drops required mobile copy.
- **R3-012 (low)** `app/s/[key]/page.tsx:112` — mobile moves the countdown outside the top bar.

## What to build
Copy that does not claim an account the recipient never made; restore the mobile copy from `X4AJCV`.
Reconcile the countdown placement with the frame, or record why the frame is wrong at 400 px.

## Review log
- Fixed both findings in `app/s/[key]/page.tsx`, with a new `CountdownChip` primitive in
  `components/ui.tsx`, and two `e2e/recipient.spec.ts` tests that fail against the pre-fix code
  and pass against the fix.

## Choices

- **The growth hook drops "account"/"sign-in" instead of restoring `X4AJCV`'s exact string.**
  `Get('kpfrb', ...)` on `X4AJCV` (mobile) itself returns `"Same sign-in you used to open this."`,
  and `Get('olGFx', ...)` on `XhRxB` (desktop) returns `"Make your own archive with the same
  account you used to open this. Nothing you have read here comes with you."` — both masters carry
  the same false account claim R3-009 flags, so "restore the mobile copy from `X4AJCV`" cannot mean
  copying that string verbatim without reintroducing the defect. Shipped copy instead keeps every
  frame's structure (title, a short mobile line, a longer desktop line, the "Nothing you have read
  here comes with you" data-separation sentence) and drops only the false account clause: mobile
  now reads "Nothing you have read here comes with you.", desktop "Make your own archive. Nothing
  you have read here comes with you." Confidence 75 — sound; the settled decision in CLAUDE.md
  ("recipients need no account") overrides the frame here, and H-5's own story says "where this
  story's prose and the frame disagree, read the frame and say so" but is silent on a frame that
  disagrees with a settled product decision, so this is the reading applied.
- **Mobile gets a new compact `CountdownChip`, not the full `Countdown` card moved into the top
  bar.** The code's prior comment claimed the full 56px `Countdown` card is too wide for the 64px
  top bar at mobile widths. Reading frame `X4AJCV` directly (`Get('X4AJCV', ..., {depth:4})`) shows
  its top bar (`g1smg8`, 74px) already contains a 30px, single-line, rounded-full pill
  (`Y57h2`: calendar glyph + one date label, no state word, no remaining-time column) beside the
  wordmark — a different, smaller component from `Countdown`, not the same one resized. `XhRxB`'s
  desktop top bar carries the same kind of compact pill (`RI6Ng`, 32px) rather than the full card
  too, but R3-012 only names the mobile placement, so the desktop slot (`hidden md:block`, still
  the full `Countdown`) is left unchanged to keep this fix scoped to the finding. Confidence 70 —
  sound for the mobile fix; needs-user on whether desktop's top-bar slot should also move to a
  compact pill for full frame fidelity — provisional call applied: leave desktop as-is, since R3-012
  is rated low and desktop was not flagged.
- **`CountdownChip` never shows the `closing`/`active` word or the remaining-time count the full
  `Countdown` card shows.** The only pill instance read from either frame is in the `active` state
  ("Ends 4 December", no urgency treatment), so there is no frame evidence for how a compact pill
  should render `closing` urgency. Shipped it with the same neutral ink/navy styling at every
  state, swapping only the label text (`Access ended` when expired). Confidence 55 — needs-user;
  provisional call applied: no color-coded urgency in the compact pill, reversible by adding
  `COUNTDOWN_SPEC`-driven coloring later if an urgent-pill frame instance turns up.
