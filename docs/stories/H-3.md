# H-3 — Chrome — rail, tab bar, breakpoints

## Story
- HealthSend is laid out for a browser window and holds together down to a phone. Three
  breakpoints, and the app currently has none of them — every page is a centred `max-w-2xl`
  column.

## Context
Depends on: H-1.

`DESIGN.md` § Layout, § Rail, § Top bar (recipient), and Sheet 0 § *Desktop first, then the
phone* (`e14T8q`).

What changes between desktop and mobile, **and nothing else does**: the 264px rail becomes the
three-tab bottom bar on `$glass-raised`; two columns become one; Display drops 44 → 34; the inset
drops 48 → 20; tables become stacked rows. Content, copy and component vocabulary are identical.
If a mobile screen says something its desktop twin does not, one of them is wrong.

The recipient surface has its own chrome — a top bar with the wordmark and the countdown, no rail,
no tabs. A recipient has no account and no navigation.

## Reading the design

**`healthsend.pen` is the source. A screenshot of it is not.** Read the nodes with the
`mcp__pencil__execute` tool against `<repo>/healthsend.pen`:

```js
Print(JSON.stringify(Get("<a frame id named in this story>", {depth: 6}), null, 1))
```

- `Get(id, {depth: n})` returns exact geometry, fills, strokes, corner radii, gaps, padding, font
  family, size and weight — and the `$token` references **by name**. None of that survives a
  screenshot, and guessing it is how a build ends up approximately right and visibly off.
- Add `resolveInstances: true` to expand component instances; the ids that come back are
  `instanceId/childId` paths you can read further.
- `Get(id, (n, c) => Print(n.name, c.bounds.width, c.bounds.x))` gives resolved bounds in the
  parent's coordinate space. Use it to check alignment and spacing rather than measuring pixels by
  eye. `c.problems` flags anything clipped by its parent.
- **Copy every string verbatim from the `content` fields.** Re-typing copy from an image is how a
  claim that was deliberately corrected gets silently restored — that has already happened once in
  this project, which is why H-20 says so explicitly.
- `TakeScreenshot([id])` is for confirming your build matches after you have read the nodes. It is
  never the input.

**Read only.** Never call `Insert`, `Update`, `Copy`, `Replace`, `Delete`, `Move`, `SetVariables`
or `Generate` against the canvas, and never commit `healthsend.pen`. The pencil MCP server drives
the operator's live editor, not your worktree's copy of the file — a write from a worker lands in
their open document. The design is an input to this story and an output of none.

Node ids named in this story are stable and can be read directly. The frame is the contract; where
this story's prose and the frame disagree, read the frame and say so in `## Choices`.

**Routing:** this story needs a worker whose engine has the `pencil` MCP server. It is configured
globally on this machine, so a Claude worker in a worktree inherits it; an engine without it can
only see exported images and must not be given this story.


## Review log

## Choices

- **Selected rail-item icon weight: `fill`, not the frame's `400`.** The rail frames
  (`ACUf3`/`HMa4U`/`hCcwO`/`LKFS1`, node `C88DJR` and its siblings) store the selected
  item's icon at a numeric weight of `400`, which is Phosphor's `regular`, not `fill`.
  DESIGN.md's Rail section reads "Fill-weight icon" for the selected item, and H-1's
  `TabBar` (pen id `kGlX0`, already in `components/ui.tsx`) already implements
  "fill when active, light when not" for the same selected/unselected relationship.
  Followed DESIGN.md's text and the `TabBar` precedent over the numeric frame value, so
  the rail and the tab bar say the same thing about a selected destination. If wrong,
  it is a one-line change (`weight={isActive ? "regular" : "light"}` in
  `components/chrome.tsx`'s `Rail`).
- **The icon-only rail (768–1279px) shows no wordmark at all**, rather than a
  compact mark. No frame exists at that width — DESIGN.md only describes it in prose
  ("Icon rail, labels become tooltips on hover") — and inventing a mark not in
  `healthsend.pen` risks becoming a second, undrawn identity for the brand. Hiding the
  text entirely until `xl` (1280px) was the smaller claim.
- **The New Share button's icon weight follows the frame literally (`regular`/400,
  node `cVBxg`)**, unlike the rail items above — there is no competing DESIGN.md prose
  about button icon weights specifically, so nothing overrides the frame here.
- **Nav destinations are wired through an `onNavigate` callback, not `next/link`.**
  The archive/shares/assistant routes do not exist in this repo yet (they are H-17/H-10/
  a later story), and the non-goals rule out a router abstraction. A callback lets a
  screen decide what "navigate" means without this chrome assuming routes that are not
  built. Whoever wires real navigation later can call `router.push` (or a `<Link>`)
  from inside the callback with no change to `chrome.tsx`.
- **A new `app/chrome-preview/` route was added as a review harness.** `app/kitchen-sink/`
  was off-limits, and the contract's own verification step ("check both widths yourself")
  needs a rendered surface with the rail, the tab bar and the recipient top bar all in
  view at once. It renders placeholder content only, per the chrome's own contract
  ("does not hardcode any screen's content") — it is scaffolding for review, not a sixth
  screen, and can be deleted once a real screen composes into `SenderChrome`.
- **The recipient top bar drops the mobile frame's extra top padding and safe-area
  allowance** (`dzqQ7`'s 22px top padding vs. the desktop frame's flat 0) in favour of
  one 64px bar with the same 20/32/48px screen-inset horizontal padding used everywhere
  else in this story. The two frames disagree on this point and neither this story nor
  DESIGN.md's prose says why; matching the already-established inset scale seemed safer
  than inventing a second, one-off spacing rule for a single component.
