# H-22 — Stage 4 — the assistant

## Story
- Connect the assistant you already use to a slice of your archive for a set number of weeks. It
  answers from real numbers, is never told whose they are, and on the date you chose it stops
  being able to.

## Architecture, decided 2026-09-12 — remote MCP, real tools over scoped records, passkey-derived auth

**This reverses `DESIGN.md` § Why the connector is local, and not a remote endpoint.** That section
still reads *"decided, don't reopen"*. Rewriting it is part of this story: leaving a reversed
decision documented as settled is how the next person rediscovers the argument from scratch.

**Why the reversal is legitimate.** The original objection was *"no gatekeeper anywhere, including
us"*. That premise died with the split-key rewrite — the holder is ours, it sits in the read path,
and it can be compelled; the README says so plainly. The live question is no longer *whether* a
server of ours exists, but *how much capability* it holds.

| | holds | if compelled |
|---|---|---|
| Holder (shipped) | half a content key, no ciphertext | nothing — cannot decrypt alone |
| Remote MCP that decrypts | a whole capability, continuously, for weeks | everything in scope |
| **Remote MCP, scoped records, encrypted at rest (this)** | one grant's slice, key only in the bearer token | the store alone: ciphertext. A live server mid-session: that grant's slice |

**What is stored remotely — the scoped records, not a summary.** The assistant needs real tools
over the real shapes: markers with units and reference ranges, nightly series over a range, training,
medications, notes. A precomputed summary can only answer what was materialised, which is not an
assistant, it is a paragraph. So at consent the **browser** decrypts the selected records and pushes
that slice — and only that slice — to the endpoint.

**The endpoint never holds a key, and never holds the archive.** That is the distinction that
matters, and it is the one `DESIGN.md` was actually protecting. A server that *decrypts* holds a
capability over everything its key opens, for as long as it holds the key. This server holds a
copy of what one grant scoped, and nothing else — no key, no ciphertext it could widen, no path to
the rest of the archive.

**Encrypt the slice at rest, and put the key in the capability.** Store the scoped records
encrypted; the token the assistant bears carries (or derives) the decryption key; the endpoint
decrypts per request and persists the key nowhere. A dump of the store is then ciphertext with no
key beside it, which is the difference between "a breach exposed the database" and "a breach
exposed health records".

**The honest residual.** A server that answers questions must see the answer while it answers.
During an active grant, a compelled or compromised *running* server sees that grant's slice. No
design removes this — it is what having a remote assistant costs — and it must be said plainly on
4.1 rather than implied away. What it is bounded by: one grant's scope, and the grant's expiry.

**Tool surface.** Every tool is scope-checked against the grant on every call, and the grant's
expiry is checked before anything is served — the same discipline as `lib/unlock.ts`, which asks
Arkiv rather than keeping its own clock. At minimum: what this grant may read (so the assistant can
tell the user what it has), blood panel markers with ranges, a wearable series over a range, and
whatever `lib/archive.ts` models by then. An out-of-scope call is refused, not silently emptied.

**Auth is the existing signature scheme, not OAuth 2.1.**

- `signedMessage(action, entityKey, timestamp)` in `lib/revoke.ts` already namespaces by action —
  use `"mcp"`. A signature captured for another action must not verify here, and that property is
  already covered by `verify:revoke`.
- **The assistant cannot sign.** The passkey lives behind the Swarm ID iframe, and Claude reaches
  the endpoint from Anthropic's cloud. So the browser signs **once, at consent**, and mints a
  short-lived capability bound to the grant's expiry, which the assistant then bears. That is the
  same shape as a share link: the browser mints, the bearer presents. **It is also exactly what the
  pairing code in 4.2 is** — the auth handoff, not a convenience.
- **Derive a per-grant pseudonym with `blindAttribute`, never the stable derived address.** A
  constant identifier would let the endpoint link every assistant session a person ever opens, and
  for health data linkability is the disclosure.

**Pseudonymous — never "anonymous", and not "pseudo-anonymous" either.** `DESIGN.md` § Words we use
bars the claim because health data re-identifies: a rare marker profile with a date narrows to one
person whatever the key is called. Say the true thing — *the assistant is never told whose numbers
these are* — which is a statement about what we send, not about what can be inferred from it.

**What this costs, stated plainly.** The endpoint is internet-reachable and needs rate limiting and
abuse handling. Expiry depends on our infrastructure again — the same trade already accepted for the
holder, so it is consistent rather than new. And the store holds real health records for the life of
a grant, which is a larger thing to defend than a row of half-keys: encryption at rest with the key
held only by the bearer is what keeps a breach of it from being a breach of the data.

It also expires, which makes it strictly better than 4.4's paste fallback — the one surface in this
product that never can, because text pasted into a conversation cannot be recalled.

## Screen scope, set by the operator 2026-09-12

**Build the connector *setup*, not the *download*.**

In: **4.1** the consent screen, the **pairing code** portion of 4.2, **4.3** the connected state, and
the **2.4** sheet explaining the permission before it is given.

Out: everything in 4.2 that the design itself calls *"a flow we only half control"* — the
`healthsend-connector.mcpb` download, the browser's download shelf, the Finder, the assistant's own
install dialog, *"look in your Downloads folder"*, *Download again*, and the three named install
failures. None of those surfaces is ours, and a walkthrough for installing a bundle that does not
exist is worse than no screen.

4.4, the paste fallback, is deferred with the download: it is the product's only non-expiring
surface and it earns its place as an escape hatch from a connector that will not install — which is
precisely the flow being cut.

What remains is the part that is actually the MCP connection and the part that carries the security
decision: what the assistant may read, for how long, the code that pairs it, and the live state
afterwards.

## Reading the design

**`healthsend.pen` is the source. A screenshot of it is not.** Read the nodes with the
`mcp__pencil__execute` tool against `<repo>/healthsend.pen`:

```js
Print(JSON.stringify(Get("<a frame id named in this story>", {depth: 6}), null, 1))
```

- `Get(id, {depth: n})` returns exact geometry, fills, strokes, corner radii, gaps, padding, font
  family, size and weight — and the `$token` references **by name**. None of that survives a
  screenshot, and guessing it is how a build ends up approximately right and visibly off.
- Add `resolveInstances: true` to expand component instances; the ids that come back are
  `instanceId/childId` paths you can read further.
- `Get(id, (n, c) => Print(n.name, c.bounds.width, c.bounds.x))` gives resolved bounds in the
  parent's coordinate space. Use it to check alignment and spacing rather than measuring pixels by
  eye. `c.problems` flags anything clipped by its parent.
- **Copy every string verbatim from the `content` fields.** Re-typing copy from an image is how a
  claim that was deliberately corrected gets silently restored — that has already happened once in
  this project, which is why H-20 says so explicitly.
- `TakeScreenshot([id])` is for confirming your build matches after you have read the nodes. It is
  never the input.

**Read only.** Never call `Insert`, `Update`, `Copy`, `Replace`, `Delete`, `Move`, `SetVariables`
or `Generate` against the canvas, and never commit `healthsend.pen`. The pencil MCP server drives
the operator's live editor, not your worktree's copy of the file — a write from a worker lands in
their open document. The design is an input to this story and an output of none.

Node ids named in this story are stable and can be read directly. The frame is the contract; where
this story's prose and the frame disagree, read the frame and say so in `## Choices`.

**Routing:** this story needs a worker whose engine has the `pencil` MCP server. It is configured
globally on this machine, so a Claude worker in a worktree inherits it; an engine without it can
only see exported images and must not be given this story.

## A claim this story will make false — found folding H-21, 2026-09-12

`components/sign-in-screen.tsx` renders the sign-in frame's copy verbatim, and it includes:

> This creates an account only you can open. We hold no password, no email list and **no copy of
> your health data** — there is nothing here for us to hand over or lose.

It is true today. The holder keeps half a content key, which opens nothing on its own; the
ciphertext sits on Swarm, which is not us.

**This story ends that.** The endpoint holds one grant's scoped records — real markers, real
series — for the life of that grant. Encrypted at rest with the key in the bearer token, which is
what keeps a breach of the store from being a breach of the data, but *held* all the same.

So the sentence has to change with the feature, on both frames (`BsnX6` desktop, `GdIlc` mobile —
the mobile form already drops the "hand over or lose" clause). Do not leave it standing. It would
be the fifth false claim this product has shipped, and unlike the previous four it would be one we
walked into with the reasoning already written down.

The honest version is narrow and specific: nothing is held **unless you connect an assistant**,
and then only what that grant scopes, only until it expires. That is a better sentence than the
one it replaces, because it is checkable.
