# H-63 — The archive can hold PDFs, and Add takes several at once

## Story
- Pick one or more PDFs in a single step and they land in your archive as documents, still there after
  a reload and on another device.

## Why this is split from H-64
The share side edits the compose screen, which H-60 is changing. This half does not, so it runs now.
H-64 (share from archived PDFs) starts once this and H-60 have merged. The original combined story is
`docs/stories/H-62.md`; its **Operator decisions** and **consequence** sections apply to both halves.

## What to build
- **A document record kind** in `lib/archive.ts`: encrypted PDF bytes plus display name, size, and
  added date. It must round-trip through `createArchive` / `addArchiveRecords` / `openArchive` and be
  rejected by validation if malformed. It never carries provenance into a share.
- **`lib/archive-store.ts`**: add documents through the existing read-modify-write, one upload of the new
  archive version for the whole pick — not one upload per file.
- **Add: one or more PDFs in one pick.** `multiple`, `accept="application/pdf,.pdf"`. Check each file
  starts with `%PDF-` and reject any that does not, saying which. Replace the "stays in this browser.
  Only its parsed readings are encrypted and stored" copy — for a PDF the document itself is encrypted
  and stored.
- **Your archive** shows the added documents (name, date, size) in the right group.

## Evidence
In a browser: pick two PDFs in one go, add them, **reload**, and see both listed in Your archive. A
non-PDF renamed `.pdf` is rejected. A proof that a two-PDF add performs exactly one archive upload.

## Non-goals
- Sharing them (H-64). Removing them (H-18, paused).
