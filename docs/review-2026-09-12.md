## H-11 — `79da8e2`, `edc0c0d`

### Critical — A recipient can restore a share after the sender ends it

- **Location:** `app/api/holder/share/route.ts:40`; `lib/holder-store.ts:69`; `lib/holder-store.ts:83`
- **Confidence:** 99
- **Failure scenario:** A recipient opens a live send and keeps the holder share that the browser receives. The sender ends access. This deletes the Redis key but leaves the Arkiv grant live. The recipient then posts the saved share and the public commitment to the unsigned share route. `SET NX` succeeds because the key is absent. The same link opens again until the Arkiv grant expires.
- **Defect:** The write-once rule has no permanent revoke state. The share route also has no sender authorization. Revocation is therefore reversible by the recipient.
- **Evidence:** A local Upstash-compatible probe called the real `putShare`, `deleteShare`, and `putShare` functions. It returned `{"firstStore":true,"afterRevokeStore":true,"operations":["set","del","del","set"]}`.

### Critical — An unlock can return a share after revoke reports success

- **Location:** `lib/unlock.ts:91`; `lib/unlock.ts:105`; `lib/revoke.ts:140`
- **Confidence:** 99
- **Failure scenario:** An unlock reads the share. Before it returns, the sender revokes the send. Revoke deletes the key and reports success. The paused unlock then resumes and returns its in-memory copy of the share.
- **Defect:** Share read and deletion are not serialized. The statement that access ends when the sender taps the control is false for an unlock that is already in progress.
- **Evidence:** A local race probe paused the real `resolveUnlock` after it read the share. The real `performRevoke` returned `{"ok":true}` and deleted the share. The paused unlock then returned `{"ok":true,"share":"in-memory-share"}`.

## H-12 — `ce297aa`

### High — The sender cannot see the access log in the product UI

- **Location:** `app/api/holder/access-log/route.ts:15`
- **Confidence:** 100
- **Failure scenario:** A recipient opens a send twice. The sender opens the app and checks the active send. The page shows no “When she looked” entries and makes no access-log request.
- **Defect:** The story requires that the owner sees the entries. The change adds an API and a proof only. No product component reads the API.
- **Evidence:** A repository search finds access-log reads only in the route, library, and proof. It finds no call from `app/page.tsx` or another UI component.

### High — A served unlock can leave no access record

- **Location:** `lib/unlock.ts:105`
- **Confidence:** 100
- **Failure scenario:** Redis rejects the log write while Arkiv and the holder share are available. `resolveUnlock` catches the error and still returns the share. The recipient reads the document, but the sender later sees no entry.
- **Defect:** The story requires one record for each served unlock. The implementation makes the record best effort and explicitly accepts missing entries.
- **Evidence:** `pnpm verify:log` reports `PASS  a record-write failure still serves the share` and finishes with `All checks passed.`

### High — A failed TTL write can retain an access record permanently

- **Location:** `lib/holder-store.ts:102`
- **Confidence:** 99
- **Failure scenario:** Redis accepts `RPUSH` and then rejects `EXPIRE`. No later unlock occurs. The timestamp list remains without a TTL, although the story says that the log expires with the share.
- **Defect:** The data write and TTL write are separate operations. Failure of the second operation does not undo the first.
- **Evidence:** A local Upstash-compatible probe accepted `RPUSH` and rejected `EXPIRE`. The real `recordAccess` rejected after the timestamp had already been stored.

### Medium — The access-log proof does not connect writes to reads

- **Location:** `scripts/access-log-proof.mjs:101`
- **Confidence:** 100
- **Failure scenario:** The Redis writer stores the wrong key, overwrites earlier entries, or writes no entries. The read test still returns two entries because its fake returns a prebuilt `opened` array that did not come from the earlier write test.
- **Defect:** The proof tests a recording callback and a separate read callback. It does not prove that the production storage preserves two real opens and returns them to the owner.
- **Evidence:** The write test stores events in `recorded` at line 43. The read test creates an unrelated `opened` array at line 105 and returns it directly at line 106.

### Medium — One captured access-log signature can read the log more than once

- **Location:** `lib/access-log.ts:40`; `lib/revoke.ts:48`
- **Confidence:** 99
- **Failure scenario:** A proxy, extension, or log captures a valid access-log request. It sends the same body again within five minutes. Both requests pass signature recovery and both read the sender's timestamps.
- **Defect:** The message has an action, entity key, and timestamp, but it has no server challenge or used-signature state. Freshness limits replay duration; it does not stop replay.
- **Evidence:** A probe sent one signed request object twice to the real `readAccessLog`. It returned `{"first":true,"replay":true,"storageReads":2}`.

## H-25 — `63f7fef`

### High — An HTTP 404 from the Arkiv RPC is shown as expiry

- **Location:** `lib/arkiv.ts:249`; `lib/sends.ts:201`
- **Confidence:** 100
- **Failure scenario:** The configured RPC path is wrong, a proxy returns HTTP 404, or the endpoint is temporarily unavailable with a 404 response. `isNotFound` matches the transport error text. `getGrant` returns `null`, and the recipient sees “This link has expired.”
- **Defect:** The code confuses an HTTP endpoint failure with an Arkiv “no live entity” result. This violates the required distinction between expiry and infrastructure failure.
- **Evidence:** A local RPC server returned HTTP 404 for every request. Calling the real `getGrant` returned `{"rpcStatus":404,"getGrant":null}`.

### High — A rejected holder fetch is shown as a decryption error

- **Location:** `lib/sends.ts:231`; `lib/sends.ts:263`; `app/s/[key]/page.tsx:328`
- **Confidence:** 100
- **Failure scenario:** The browser cannot connect to `/api/holder/unlock`, so `fetch` rejects before it returns an HTTP response. The outer catch returns status `error`. The page then says that the grant was found but the document would not decrypt, instead of “Temporarily unavailable.”
- **Defect:** The unavailable branch only handles completed 5xx responses. It does not handle network rejection, which is the normal shape of an unreachable holder.
- **Evidence:** The fetch starts at `lib/sends.ts:231`. Only a returned response is classified at lines 237-245. A thrown fetch error reaches the generic catch at lines 263-264.

### Medium — A malformed live Arkiv entity is shown as expiry

- **Evidence:** `toGrant` returns `null` for a missing reference at line 265 and for every caught parse error at lines 285-286. `openSend` maps all `null` values to `expired` at `lib/sends.ts:201`.

## Checks that were sound

- The signed messages bind the action, lowercase entity key, and timestamp.
- Malformed signatures are rejected. Address comparison is case-insensitive.
- The no-grant revoke branch does not delete holder data.
- A revoke signature cannot authorize an access-log read.
- Unlock asks Arkiv before it reads the holder share.
- Unlock does not keep a private expiry timer.
- Commitment comparison processes fixed-length SHA-256 hexadecimal strings.
- A holder share plus the authentication key cannot reconstruct the content key.
- A v2 Arkiv payload stores a commitment and no key material.
- Access-log payloads contain timestamps only.
- A wrong-owner access-log request does not read storage.
- H-1 exports and renders all nine required primitives.
- The compiled H-1 colors, radii, and shadows resolve. The cyclic-token concern from the earlier review was false.
- The H-23 notice meets its placement and warning requirements.
- H-24 states the testnet and onboarding limits.
- H-25 reaches all five named initial states.
- The H-25 fixture uses the production crypto and envelope primitives.
- The commit hook checks author and committer name and email.
