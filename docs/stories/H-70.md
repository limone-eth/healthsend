# H-70 — The archive shows stale lists and can overwrite its own last edit

## Story
- Add or remove a PDF and the list shows the result at once. Make a second change straight after and
  both changes survive.

## What happened (operator's browser, 2026-09-13, localhost, real Swarm)
Three mock PDFs were added in one pick:
1. "Encrypting and adding 3 PDFs…" showed, then cleared with no error, and the list still said
   **1 BLOOD TEST**.
2. A full reload a minute later showed all four.
3. The same thing happened earlier after a removal. The sheet closed, and the row stayed until a
   later reload.

## Why
Every change reads the archive, edits it, reseals it, uploads it, and moves the private feed
(`lib/archive-store.ts`: `readStoredArchive` → edit → `uploadEncryptedBlob` → `writeArchiveReference`).
Two paths then read the feed again, and **Swarm feed reads lag behind feed writes**:
- **The list is stale.** `app/(sender)/page.tsx` ignores the `Archive` that `addRecordsToMyArchive` /
  `removeDocumentFromMyArchive` already return, and calls `refreshArchive()`, which calls
  `loadMyArchive()`, which reads the old reference.
- **Edits can be lost. This is the serious one.** The next change starts with `readStoredArchive`. If
  the feed still points at the previous version, the change is made on the old archive and written on
  top. The edit just made disappears silently: PDFs added a moment ago vanish, a removed PDF comes back,
  a share-index entry is dropped. The share-index write in `createSendFromArchive`
  (`recordShareInArchive`, `lib/sends.ts`) reads the same way. So does removing a PDF right after
  sharing it.

## What to build
- **Never start from an older archive than this device last wrote.** The archive needs an ordering it
  carries itself, because a feed reference alone can't be ordered.
  - Suggested: a monotonically increasing `rev` (and `updatedAt`) inside the sealed `Archive`, bumped
    on every write. Keep it backward compatible: an archive without `rev` opens as `rev: 0`.
  - The store remembers the last archive this device wrote, keyed by the identity's archive topic.
    Keep it in memory, plus `localStorage` so a reload survives the lag. Store the Swarm reference
    and `rev`, never plaintext or key material.
  - Every read (`loadMyArchive`, and the read inside each write) fetches both the feed's reference
    and that remembered reference, and uses whichever opens to the higher `rev`.
  - Another device's newer write still wins because its `rev` is higher. Record under `## Choices`
    what happens when two devices write the same `rev`.
- **One write at a time.** Serialise every archive write in the tab: add, remove, and share-index
  entry. A second pick while the first is uploading, or a share finishing while a removal is in
  flight, queues rather than races.
- **Show the result straight away.** The archive page renders the `Archive` each write returns. It
  re-reads only on first load, and never lets a slower re-read replace a newer result.
- **The picker while adding:** the Add buttons are already disabled. Check a queued second pick
  can't bypass that.

## Evidence
- **Offline proof, run red first** (the `scripts/*-proof.mjs` pattern with the store's dependency
  injection):
  - a feed stub that returns the previous reference for the next N reads after a write;
  - add A, then add B, then remove A. The final archive holds exactly B, and so does a fresh
    `loadMyArchive` while the feed is still lagging;
  - two concurrent adds both survive;
  - an old archive without `rev` still opens and upgrades.
- **E2E:** extend `fulfillArchiveBackend` (`e2e/archive-persistence.spec.ts`) with a lagging feed
  mode. Pick two PDFs, then one more straight away, and the list shows all three without a reload.
  Remove one and the row goes at once. Reload in a fresh context and the final state is there.
- `pnpm lint`, `pnpm build`, `pnpm exec tsc --noEmit`, `pnpm test`, every non-live `verify:*` lane pass.

## Review log

## Choices

- **Two devices writing the same `rev`.** `readStoredArchive` (`lib/archive-store.ts`)
  opens both the feed's reference and this device's remembered reference whenever
  they disagree, and keeps whichever opens to the higher `rev`. On a genuine tie —
  same `rev`, different references — the feed's reference wins. This is a real
  conflict the scheme does not resolve: two devices both started from the same base
  archive and each wrote a `rev` one higher, so one of the two edits is silently
  kept and the other silently dropped, exactly as a last-write-wins scheme would.
  `rev` orders writes from a single device against Swarm's own lag; it is not a
  merge protocol for concurrent writers on different devices. That case is out of
  this story's scope (Story only asks for "add or remove... shows the result at
  once" and "make a second change straight after," both single-device), so this
  is recorded as a known limit rather than fixed here.
- **What "one write at a time" covers.** Serialisation (`serialized`,
  `lib/archive-store.ts`) is a module-level promise chain, so it covers every write
  in one JS module instance — one browser tab. It does not, and cannot, serialise
  writes across two open tabs of the same origin, or across two devices; those are
  the same "two devices write concurrently" case above, at a shorter time scale.
- **Where the remembered write lives.** Keyed by `toHex(identity.archiveTopic)` in
  both an in-memory `Map` and `localStorage`, never by a per-record or per-page key.
  One entry per identity is enough because the whole archive is one sealed blob;
  there is nothing finer-grained to remember.
