# H-39 — A send writes its grant before discovering the holder is unusable

## Story
- Creating a send spends gas and writes a permanent Arkiv entity, and only *then* contacts the
  holder. When the holder is unreachable the user is told *"The grant was written but the key share
  was not stored, so this send cannot be opened"* — which is accurate, and far too late.

## Context
Hit in the running app on 2026-09-12, not by a test. `KV_REST_API_URL` held an 11-character
placeholder locally, so every send failed this way.

`lib/sends.ts` orders the work: encrypt → Swarm upload → **`createGrant`** (line 118) → holder
handoff (line 141). The grant is an on-chain write with real gas and a permanent transaction. The
holder is never touched until after it lands.

**`holderConfigured()` is the other half of the problem:**

```ts
return Boolean(process.env.KV_REST_API_URL && process.env.KV_REST_API_TOKEN)
```

An 11-character placeholder is truthy, so the guard passes and the failure surfaces as a raw
`UrlError` from deep inside the Upstash client — a 500, not the 501 the route has a message for.

## What to build
- **Check the holder before writing the grant.** A cheap preflight — the same
  configuration/reachability check the route already wants to make — run at the top of
  `createSend`. If the holder cannot serve, nothing is uploaded, no gas is spent, and nothing is
  written on-chain.
- **Validate the shape, not just the presence.** `KV_REST_API_URL` must parse as an `http(s)` URL.
  A placeholder should fail as *"no holder configured"* (501), which is a sentence a user can act
  on, rather than as a stack trace.
- Keep the existing post-handoff throw. It is the correct failure for a holder that dies mid-send,
  and its message is honest. This story is about not reaching it for a holder that was never alive.
- **Order the ciphertext upload too.** A Swarm upload before a doomed send leaves a paid-for blob
  nobody can open. Cheaper than a grant, still waste.

## Also
`.env.example` did not mention `KV_REST_API_URL` or `KV_REST_API_TOKEN` at all, while the holder is
load-bearing — anyone cloning this repository got a send flow that fails at the last step with no
hint why. Fixed alongside this story's discovery, together with `docker-compose.dev.yml` and
`pnpm holder:up`, which runs a real Redis behind an Upstash-REST shim so local and production share
a client, the Lua scripts and the atomicity guarantees.
