# H-34 — Tests that pass without testing
## Story
- Six tests do not test what they are named for. One of them would pass while the storage it covers
  wrote to the wrong key entirely.

## Context
From the adversarial review, which was asked to attack the tests as hard as the code because this
repository has previously shipped a `PASS` that asserted only that some buffers were non-empty.

- **`scripts/access-log-proof.mjs:101` — the read test does not read what the write test wrote.**
  The write test stores events in `recorded`; the read test builds an unrelated `opened` array at
  line 105 and returns it at 106. A writer that stored the wrong key, overwrote entries, or wrote
  nothing would still pass. This is the vacuous-test class, found again.
- **`scripts/revoke-proof.mjs` does not independently test entity binding** — that a signature for
  one entity key cannot end another. That property is the reason the key is in the message.
- **The offline network guard does not prove the lane is offline.** Route abort is not an
  assertion, and the helper allows every same-origin route rather than only page assets and the
  mocked holder.
- **Route stubs accept wrong request values**, so a caller sending the wrong body still passes.
- **The multi-document test never opens the second document.**
- **Expiry while a document is open is untested** — the countdown closing the page under a reader
  is a product behaviour with a comment explaining why it matters.

## Added after H-29 (2026-09-12)

- **The proofs test decision logic against fakes, and never the real storage.** Demonstrated: with
  `isRevoked` in `lib/holder-store.ts` edited to `return false` — disabling the tombstone that H-29
  added to close a critical hole — `pnpm verify:revoke` still reported **11/11 passing**. The test
  named *"revocation is permanent"* uses `fakeHolder()`, which reimplements tombstone semantics in
  memory, so the real implementation is never called.

  The real `putShare` does check `isRevoked`, verified by reading it, so the fix is sound. But
  nothing would catch it if that check were removed or reordered, and that is the second time today
  a proof has been found asserting against its own fixture rather than the code under test — the
  first was `access-log-proof.mjs`.

  Fixes worth considering: a contract test that runs the same cases against the real
  `holder-store.ts` backed by an in-memory Redis-compatible double, or a check that the fake and
  the real module satisfy one shared interface test.

## Narrowed by H-32 (2026-09-12)

H-32 closed most of this for the holder: `lib/holder-store.ts` now exposes an injectable
`HolderClient`, and `scripts/access-log-proof.mjs` drives the **real** store functions against one
shared in-memory Redis, so the read side is proven to see exactly what the write side stored. The
write/read disconnect flagged above is gone, and `verify:log` went 7 → 12.

**One gap remains, and it is now precise.** The three atomic bundles are Lua scripts sent via
`eval()`. The fake matches on the exact script constant imported from the module — so it cannot
drift from a retyped copy — but it then implements each script's semantics in JavaScript rather
than interpreting Lua. Demonstrated: deleting the tombstone guard

```lua
if redis.call("EXISTS", KEYS[2]) == 1 then return 0 end
```

from `PUT_SHARE_SCRIPT` leaves every proof green, because the fake's JS branch still enforces it.

So what is unverified is no longer "the storage layer" but "six lines of Lua". That is a large
improvement and a real residual: a typo in a script body ships silently. Closing it needs either a
Lua interpreter in the fake, or a contract test against a real Redis in CI. Worth deciding which,
not worth pretending it is covered.

## What to build
Fix each so it fails when the named behaviour breaks. For each one, demonstrate the failure first —
break the code, watch the test go red, restore it — and record that in the story's Choices ledger.
A test that has never been seen to fail is a claim, not a check.
