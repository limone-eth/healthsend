# H-67 — Point the Chipotle adapter at Lit's real API

## Story
- H-65 built the Chipotle provider without network access and said so: its HTTP client and the enclave
  calls inside the Lit Action are placeholders. This story replaces them with Lit's documented API, so
  the live probe can get past `credentials` and actually exercise the release gate.

## What H-65 guessed, and what Lit documents
Verified 2026-09-12 against `https://api.chipotle.litprotocol.com/core/v1/openapi.json` and
`developer.litprotocol.com`.

| | H-65 placeholder | Lit's real API |
|---|---|---|
| Base URL | `NEXT_PUBLIC_CHIPOTLE_ENDPOINT` + guessed paths | `https://api.chipotle.litprotocol.com/core/v1` |
| Run an action | `POST {endpoint}/actions/{cid}/execute` `{pkpPublicKey, jsParams}` | `POST /lit_action` `{code?, ipfs_id?, js_params}` — **use `ipfs_id`**, never `code`, so only the registered action can run |
| Auth header | unconfirmed | `X-Api-Key: <usage key>` or `Authorization: Bearer <usage key>` |
| List authorised actions | `GET {endpoint}/pkps/{pk}/actions` | `GET /list_groups`, `GET /list_actions`, `GET /list_wallets_in_group` |
| Compute a CID | not implemented | `POST /get_lit_action_ipfs_id` (body: the action code) — no manual IPFS pinning |
| Register the action | not implemented | `POST /add_action {action_ipfs_cid, name, description}` then `POST /add_action_to_group {group_id, action_ipfs_cid}` — **operator-run with the account key**, never from the app |
| Encrypt inside the action | `chipotleTeeEncrypt(...)` | `await Lit.Actions.Encrypt({ pkpId, message })` → ciphertext string |
| Decrypt inside the action | `chipotleTeeDecrypt(...)` | `await Lit.Actions.Decrypt({ pkpId, ciphertext })` → plaintext string |
| Params and result | `jsParams` global | `async function main({ ...js_params })`; whatever `main` returns reaches the caller |
| PKP identifier | `PKP_PUBLIC_KEY` | a **`pkpId`** — find the exact field from `GET /list_wallets` and name the env var after it |

## What to build
- Rewrite `createHttpChipotleClient` in `lib/key-release/chipotle.ts` against the table. Keep H-50's
  `KeyReleaseProvider` interface unchanged.
- Rewrite `lib/key-release/chipotle-action.js` to `main({...})` with `Lit.Actions.Encrypt/Decrypt`. Keep
  every property H-65 established: the hardcoded Arkiv RPC endpoint, the commitment cross-check before any
  Arkiv query, current state only, fail closed. The action returns only the released share, never logs it.
- **`ensureSingleAuthorizedAction` must use real data.** Read the group's permitted CIDs and fail closed
  if there is more than the one expected action, or if the group permits all CIDs.
- **A script that prints the action's CID** via `/get_lit_action_ipfs_id`, so the operator can register
  exactly that CID. The app never calls `add_action` or `add_action_to_group` — those need the account key.
- **Env vars:** rename `NEXT_PUBLIC_CHIPOTLE_PKP_PUBLIC_KEY` to whatever `list_wallets` actually returns
  (e.g. `…_PKP_ID`) and update `.env.example`. The usage key stays `NEXT_PUBLIC_CHIPOTLE_USAGE_API_KEY` — it
  is execute-only, scoped to one group, and that group permits exactly one CID, which is why it may be
  public. **The account key must never appear in any variable the app reads.**

## Evidence
- Offline proof updated to the real request shapes, demonstrated red first.
- **Live probe with the operator's credentials** (`RUN_CHIPOTLE_LIVE_PROBE=1`) records the furthest stage
  reached — AVAILABLE, or BLOCKED with the stage — and distinguishes a network failure from a genuine
  refusal. The target: a release request for a fabricated grant reaches the action and is **refused by it**.

## Non-goals
- Making Chipotle the active provider in the send/open path (the follow-up after this and H-53).
